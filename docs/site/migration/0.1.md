# Migrating from 0.0.x to 0.1

This page takes an application, a plugin library or a renderer library from the published
`@deviltea/widget-core` `0.0.6`, `@deviltea/widget-vue` `0.0.6` and
`@deviltea/widget-inspector` `0.0.4` to the `0.1` line. While the packages are `0.x`, a breaking
change bumps the minor version, so `0.1` is the line that carries every breaking change below.
Read [Changes that will not show up as a compile error](#changes-that-will-not-show-up-as-a-compile-error)
first: those are the ones a type-check does not find. The [upgrade checklist](#upgrade-checklist) at
the end gives the order in which to do the work.

Every **Before** snippet type-checks against the `0.0.x` packages and every **After** snippet
type-checks against `0.1`; the snippets marked as runnable also run. Every **Find** pattern is
[`rg`](https://github.com/BurntSushi/ripgrep) syntax and matches code written against `0.0.x`.

Each entry follows one shape: **Detect** says how the change shows itself (a compile error, a run-time
error, or nothing), **Find** gives a search that locates the affected code, and **Do** says what to
change, or states plainly that no change is needed and why. An entry that points at another one
defers to that entry's **Do**.

## Who needs to do what

| You are | Do |
| --- | --- |
| An application or host (builds Systems, compiles sources, runs Runtimes) | [Install and versions](#before-you-start-install-and-versions); the whole page, starting with the silent changes; [Stored data](#stored-data) if you persist documents |
| A plugin author (calls `createWidgetPlugin`) | The [plugin builder](#plugin-builder) entries, in particular [`emits`](#plugin-builder); the silent changes about callbacks and about [Properties that depend on Methods that emit](#a-property-cannot-depend-on-a-method-that-emits); `@deviltea/widget-core` as a peer dependency |
| A renderer author (`@deviltea/widget-vue` or your own adapter) | [`@deviltea/widget-vue`](#widget-vue), the Runtime and [exported names](#exported-names-and-types) entries, the peer dependency rules |
| An Inspector integrator (client, Agent or transports) | [`@deviltea/widget-inspector`](#widget-inspector) |
| Anyone who stores documents (sources, patches, separated sources) | [Stored data](#stored-data), [authored source](#authored-source-and-blueprint), [SourcePatch and WidgetDocument](#sourcepatch-and-widgetdocument), [separated source](#separated-source) |

## Before you start: install and versions

Upgrade all the Widget packages you use in one change, to the `0.1` line:

```bash
pnpm add @deviltea/widget-core@^0.1.0
pnpm add @deviltea/widget-vue@^0.1.0 @deviltea/widget-inspector@^0.1.0 # only the ones you use
```

All three packages are released as `0.1.0`, with `@deviltea/widget-core` published first.

- **Node `>=22.14.0`.** The packages declare `engines.node` `>=22.14.0` (it was
  `^22.14.0 || ^24.0.0`) and `sideEffects: false`. `queueMicrotask` must exist: Core reports
  listener exceptions through it.
- **`@deviltea/widget-core` is a peer dependency of `@deviltea/widget-vue` and
  `@deviltea/widget-inspector`.** `@deviltea/widget-vue` `0.0.6` depended on Core with an exact
  version; `@deviltea/widget-inspector` `0.0.4` accepted `>=0.0.3 <0.1.0`. Now both declare
  `@deviltea/widget-core` as `^0.N.0`, and a `0.1` Vue adapter or Inspector accepts only Core `0.1.x`.
  Install Core yourself, next to them.
- **Install exactly one copy of Core.** Core recognizes its own plugins, Blueprints and Runtimes by
  brands private to one loaded module, so two copies cannot use each other's objects.
  - An application installs Core once and lets the package manager resolve every dependent to it.
  - A plugin library or renderer library declares `@deviltea/widget-core` in `peerDependencies`
    (and in `devDependencies` for local work), and never bundles it. Mark it external in your
    bundler.
- **What a duplicate looks like.** `WidgetRenderer` throws `WidgetVueIntegrationError` with code
  `foreign-runtime` when it is first given the Runtime. (In `0.0.x` everything rendered and the
  first `emit` threw `WidgetIntegrationError` with code `foreign-runtime`.) `createWidgetSystem`
  throws `WidgetSystemConfigurationError` with code `foreign-plugin`, and Inspector entries throw
  `WidgetInspectionError` with a `foreign-*` code, when given an object from another copy.
- **Check for a duplicate:** `pnpm why @deviltea/widget-core`, `npm ls @deviltea/widget-core` or
  `yarn why @deviltea/widget-core` must list one version, once. Fix a duplicate with a single
  version range, `pnpm.overrides` / `overrides` / `resolutions`, or by deduplicating the lockfile.
- **Upgrade order** when you own several packages: upgrade Core first (a library publishes its
  Core peer range `^0.1.0` before an application installs it), then Vue and the Inspector, then
  the application.

## Changes that will not show up as a compile error

Each of these keeps compiling, or fails only when the code runs. Search for each one before you
run the tests.

### `RuntimeDiagnostic` and `RuntimeDiagnosticLocation` kept their names and widened

In `0.0.x` `RuntimeDiagnostic` was the union of State, Property and Method diagnostics, and
`RuntimeDiagnosticLocation` was the location of one of them. Now `RuntimeDiagnostic` is the complete
union `RuntimeLevelDiagnostic | RuntimeWidgetDiagnostic` (what `runtime.getDiagnostics()`
returns), and `RuntimeDiagnosticLocation` also covers the Runtime-level location
`{ type: 'runtime' }`. Code that used the old meaning keeps compiling in most positions, because a
narrower value is assignable to the wider type, and then reads a wider type than it expects.

- **Detect:** silent in parameter and annotation positions. A compile error where you read a
  field the Runtime-level members lack, or build a `Record` keyed by the union's codes.
- **Find:** `\bRuntimeDiagnostic(Location)?\b`
- **Do:** for every match, decide which meaning it had. A widget's or a primitive's diagnostic is
  now `RuntimeWidgetDiagnostic`; a primitive location is now `RuntimePrimitiveDiagnosticLocation`.
  Keep `RuntimeDiagnostic` only where the code handles `runtime.getDiagnostics()` output.

<!-- sample: silent-runtime-diagnostic-before before -->
```ts
import type { RuntimeDiagnostic } from '@deviltea/widget-core'

// Receives a widget's diagnostics, so it relies on the old meaning.
export function countFor(diagnostics: readonly RuntimeDiagnostic[]): number {
	return diagnostics.length
}
```

<!-- sample: silent-runtime-diagnostic-after after -->
```ts
import type { RuntimeWidgetDiagnostic } from '@deviltea/widget-core'

export function countFor(diagnostics: readonly RuntimeWidgetDiagnostic[]): number {
	return diagnostics.length
}
```

### Public Event listener exceptions are isolated

A public Event listener that throws no longer propagates to the Method that emitted. Every listener
captured when the `emit` started runs, the emitting Method completes and returns its result, and the
exception is reported asynchronously, like every other listener kind: Core rethrows it from a
`queueMicrotask` callback (an `uncaughtException` in Node, an `error` event on `window` in a
browser). Only `WidgetSystemRuntimeReentrancyError` (see [below](#emit-nesting-is-bounded)) and an
engine stack overflow still pass through.

- **Detect:** silent. A `try`/`catch` around a Method call, or a `failure` check on its result, that
  used to observe a listener's error never fires.
- **Find:** `events\.\w+\.subscribe\(` (the listeners), then the call sites of the Methods that
  emit.
- **Do:** handle errors inside the listener, or report them from the host's global error hook.

<!-- sample: silent-event-listener-before before -->
```ts
import { createWidgetPlugin, createWidgetSystem } from '@deviltea/widget-core'

const notifier = createWidgetPlugin('notifier')
	.description('A notifier widget')
	.interfaces<{ methods: { fire: (value: string) => void }, events: { change: [value: string] } }>()
	.methods(methods =>
		methods.fire({
			validateArgs: (args): args is [string] => args.length === 1 && typeof args[0] === 'string',
			execute: ({ args, emit }) => emit.change(args[0]),
		}),
	)
	.events(events => events.change({ description: 'Changed value' }))
	.done()

const system = createWidgetSystem({ plugins: [notifier] })
const blueprint = system.createBlueprint({ id: 'n', type: 'notifier' })
if (blueprint.status !== 'valid')
	throw new Error('invalid')
const runtime = blueprint.createRuntime()
const widget = runtime.getWidget('n')
if (widget === null)
	throw new Error('missing')

widget.events.change.subscribe(() => {
	throw new Error('listener failed')
})
try {
	widget.methods.fire('hello')
}
catch (error) {
	console.error('a listener failed', error) // 0.0.x: reached here
}
```

<!-- sample: silent-event-listener-after run -->

### Unknown keys on a widget node make the document invalid

A widget node has exactly these recognized own keys: `id`, `type`, `config`, `slots` and `meta`. Any
other own key is the new Blueprint diagnostic `unexpected-widget-field` (`path: [key]`), so the
Blueprint is `invalid` and creates no Runtime. In `0.0.x` extra keys were preserved and ignored
(and a typo such as `"slot"` silently dropped its content). `meta` is the reserved extension key: any
JSON value, kept in `source`, never interpreted.

- **Detect:** silent in code; at runtime `blueprint.status === 'invalid'`. Stored documents are
  the usual cause.
- **Find:** no static pattern. Compile every stored document and list the diagnostics (see
  [Stored data](#stored-data)), and read every place that builds a source object by hand.
- **Do:** move the extra data under `meta`.

<!-- sample: silent-unknown-key-before before -->
```ts
import { createWidgetPlugin, createWidgetSystem } from '@deviltea/widget-core'

const note = createWidgetPlugin('note')
	.description('A note widget')
	.interfaces<Record<never, never>>()
	.done()
const system = createWidgetSystem({ plugins: [note] })

// 0.0.x: valid; the extra key is ignored.
export const blueprint = system.createBlueprint({ id: 'note-1', type: 'note', label: 'Hello' })
```

<!-- sample: silent-unknown-key-after run -->
```ts
import { createWidgetPlugin, createWidgetSystem } from '@deviltea/widget-core'

const note = createWidgetPlugin('note')
	.description('A note widget')
	.interfaces<Record<never, never>>()
	.done()
const system = createWidgetSystem({ plugins: [note] })

const extra = system.createBlueprint({ id: 'note-1', type: 'note', label: 'Hello' })
console.log(extra.diagnostics.map(d => d.code)) // [ 'unexpected-widget-field' ]
const moved = system.createBlueprint({ id: 'note-1', type: 'note', meta: { label: 'Hello' } })
console.log(moved.status) // valid
```

### `duplicate-widget-id` split from `invalid-widget-id`, and the other changed `code` values

Code that matches on diagnostic or failure codes sees these changes. A `code` is a stable value; an
unknown code in a `switch` falls to your default branch without a compile error, and an exhaustive
switch becomes a compile error (see the per-package entries).

| Where | `0.0.x` | `0.1` |
| --- | --- | --- |
| Blueprint diagnostic, a repeated widget id | `invalid-widget-id` (with `related`) | `duplicate-widget-id` (with `related`) |
| Blueprint diagnostic, a missing or non-string id | `invalid-widget-id` | `invalid-widget-id` (no `related`) |
| Blueprint diagnostic, an extra key on a widget node | none | `unexpected-widget-field` |
| Blueprint diagnostic, a Property depends on a Method with side effects | `property-dependency-has-write-effects` (a Method that writes State) | `property-dependency-has-side-effects` (a Method that writes State or emits an Event); its message names the effect |
| `json-incompatible-value` `reason` (Blueprint and SourcePatch) | 11 values | adds `max-depth-exceeded` |
| SourcePatch failure, a patch that is not an array, an operation that is not an object, an unknown `op` | `invalid-path` | `invalid-operation` |
| SourcePatch failure, a path or `copy`/`move` operand nested too deep | none (could throw `RangeError`) | `max-depth-exceeded` |
| `WidgetSystemConfigurationError`, options that are not an object, `plugins` that is not an array, a non-function `validateStructure` | `foreign-plugin`, or an uncoded `TypeError` | `invalid-options` |
| Separated-source diagnostic `reason` | `invalid-separated-structure`: 3 values; `invalid-separated-widget`: 3 values | adds `max-depth-exceeded` and `invalid-config`, `invalid-meta`, `unexpected-field` |
| `WidgetVueIntegrationError` code | 5 codes | adds `invalid-runtime`, `foreign-runtime`, `unknown-widget` |
| `InspectorProtocolError` code | 11 codes | adds `runtime-disposed` |
| `InspectorClientError` code | the 11 protocol codes | adds `timeout` and `unknown-error` |

- **Find:** `'invalid-widget-id'|"invalid-widget-id"|'invalid-path'|'foreign-plugin'|duplicate-widget-id|property-dependency-has-write-effects`
- **Do:** read the diagnostic's `code`, and for repeated ids also `related`, then update each branch.

### `property-evaluation-cycle` lists every member of the cycle, itself included

Every `property-evaluation-cycle` diagnostic of one cycle now carries the same `related` array. It names
every member of the cycle in member order (the widgets in document order, a widget's Properties before its
Methods), including the diagnostic's own Property and any Method on the cycle. In `0.0.x` each diagnostic
got its own array that left out its own Property, and a Property that reads itself got no `related` at all;
now its `related` holds just itself, so the field is always present (`related` is required in the type).
The array and its locations are frozen, and the diagnostics of one cycle share them by identity, so a very
long cycle no longer costs memory and time that grow with the square of its length.

- **Detect:** silent. Code that reads "the other members of the cycle" from `related` now also sees the
  diagnostic's own location, and code that expected a missing `related` for a self-dependent Property
  finds a one-entry array.
- **Find:** `property-evaluation-cycle`, and any `.related` read on a diagnostic that may be one.
- **Do:** skip the entry that is the diagnostic's own Property (same `node` and `name` as `location`) where
  you want only the others. Do not mutate the array: it is shared and frozen, and a copy is yours to change.

### `deps` and `emit` callables throw outside their own callback

Inside a Method, Property or State callback, the callables you receive (`deps.*`, `emit.*`) are valid
only while **their own callback is the innermost running callback**. Called after the callback
returned or threw, from a timer or a promise continuation, from a different callback running
inside it, or while foreign code runs (a listener, a `validate`, a `default`), they throw an uncoded
`TypeError` and do nothing. After `runtime.dispose()` they throw `WidgetSystemRuntimeDisposedError`; an
`emit` callable for an Event its Method did not declare is the exception, a `TypeError` before and after
disposal. In `0.0.x` they kept working. An `emit` belongs to the one Method that received it, not to its widget: it
does not work while a different Method of the same widget runs either, even one that declares the same Event.
Consequences: nothing asynchronous can use them, the tail of an `async`
function after its first `await` cannot write State, and a Property can never write State.

- **Detect:** a `TypeError` at the call, at run time; or silent when the code swallowed errors.
- **Find:** two steps. A bare `registerDeps` match only means that the mechanism is in use, not that
  there is a problem; the risk is a `deps.*` or `emit.*` callable used after its callback returned.
  First search the files that declare `registerDeps` for constructs that defer work:

  ```bash
  rg -l registerDeps -g '*.{ts,vue}' . | xargs rg -n '\b(setTimeout|setInterval|queueMicrotask)\b|\bawait\b|\.then\(|\basync\b'
  ```

  Then search the same files for `deps` / `emit`, or a callable taken from them, that is stored or
  handed on instead of called (assigned, pushed, or passed as an argument):

  ```bash
  rg -l registerDeps -g '*.{ts,vue}' . | xargs rg -nP '[=:]\s*(deps|emit)(\.\w+)*\b(?!\s*[.(\[])|[(,]\s*(deps|emit)(\.\w+)*\s*[,)]|\.(push|set|add)\(\s*(deps|emit)\b'
  ```

  Inspect only those matches, and only the callback each one is in. The second search does not see a
  callable stored through object shorthand (`{ deps }`) or under a renamed parameter; the first one
  covers the usual cases there.
- **Do:** for each match, check whether a `deps.*` or `emit.*` callable can run after its callback has
  returned. If it cannot (the deferred work is unrelated to the callables, or the callable is only
  handed to a function that calls it before returning), no change is needed. If it can, return from
  the callback and do the later step from the host through the public Runtime surface: one ordinary
  synchronous Method call. See [Async work](../packages/widget-core#async-work).

<!-- sample: silent-deps-lifetime-before before -->
```ts
import { createWidgetPlugin } from '@deviltea/widget-core'

export const counter = createWidgetPlugin('counter')
	.description('A counter widget')
	.interfaces<{ state: { count: number }, methods: { resetLater: () => void } }>()
	.state(state => state.count({ validate: (input): input is number => typeof input === 'number', default: () => 1 }))
	.methods(methods =>
		methods.resetLater({
			validateArgs: (args): args is [] => args.length === 0,
			registerDeps: ({ dep }) => ({ setCount: dep.self.state.set('count') }),
			// 0.0.x: worked. 0.1: the callable is closed once `execute` returned.
			execute: ({ deps }) => {
				setTimeout(() => deps.setCount(0), 10)
			},
		}),
	)
	.done()
```

<!-- sample: silent-deps-lifetime-after run -->
```ts

			},
		}),

```

### A Property cannot depend on a Method that emits

A Method is read-only when it neither writes State nor emits an Event, itself or through the Methods it
invokes, and a Property may depend only on a read-only Method. In `0.0.x` only writing State counted: a
Method that only emitted was read-only, so a Property could depend on it, and reading the Property emitted
the Event (the first `get()` did, a second `get()` with nothing changed did not). Now a Blueprint in which a
Property declares a dependency on a Method that emits, directly or through the Methods it invokes, is
`invalid`: one `property-dependency-has-side-effects` diagnostic per unique Property and Method pair (two
dependencies of a Property on the same Method give one), on the Property, with `related` naming the Method the
Property invokes. The rule covers declared dependencies only: a `compute` that closes over a host widget handle
and calls one of its Methods, or over an emitter from `@deviltea/widget-core/integration`, is not stopped and
still emits during the evaluation. The compiler learns that a Method emits from
its [`emits`](#plugin-builder), so code that has not declared `emits` yet is not
rejected by this rule (and does not run either: it fails as described there).

- **Detect:** silent in code. At run time `blueprint.status === 'invalid'` and no Runtime can be created,
  for every Blueprint that contains a widget of that plugin. No type error: which Methods a Property may invoke is not part of
  the types.
- **Find:** the dependencies of Properties on Methods: `methods\.invoke\(` in the `registerDeps` of a
  Property (in a Method's `registerDeps` the same call is still allowed). Open the target Method of each
  match and check whether it, or a Method it invokes, calls `emit`. Or, with `emits` added everywhere,
  compile your stored documents and list the diagnostics with that code (see [Stored data](#stored-data)).
- **Do:** make the Property depend on something read-only. Either:
  - split the Method: keep the part the Property reads in a Method that does not emit, and move the
    `emit` into another Method with its own `emits`, which the host (or another Method) calls; or
  - let the Property depend on State or on another Property instead of on the Method; or
  - drop the Event if nothing listens to it.

  A Method may still invoke a Method that emits, and so may the host: only a Property is restricted.

<!-- sample: property-emitting-method-before before -->
```ts
import { createWidgetPlugin } from '@deviltea/widget-core'

interface LabelInterfaces {
	state: { count: number }
	properties: { label: string }
	methods: { describe: () => string }
	events: { described: [] }
}

// 0.0.x: valid, and every evaluation of `label` emits `described`.
export const labelled = createWidgetPlugin('labelled')
	.description('A widget with a label')
	.interfaces<LabelInterfaces>()
	.state(state => state.count({ validate: (input): input is number => typeof input === 'number', default: () => 0 }))
	.properties(properties =>
		properties.label({
			registerDeps: ({ dep }) => ({ describe: dep.self.methods.invoke('describe') }),
			compute: ({ deps }) => {
				const text = deps.describe()
				return text.ok ? text.value ?? '' : ''
			},
		}),
	)
	.methods(methods =>
		methods.describe({
			validateArgs: (args): args is [] => args.length === 0,
			registerDeps: ({ dep }) => ({ count: dep.self.state.get('count') }),
			execute: ({ deps, emit }) => {
				emit.described()
				const count = deps.count()
				return `count ${count.ok ? count.value ?? 0 : 0}`
			},
		}),
	)
	.events(events => events.described({ description: 'The label was described' }))
	.done()
```

```ts
				},
			})
			// The emit moved here; the host calls it when the Event should be published.
			.announce({
				validateArgs: (args): args is [] => args.length === 0,
				emits: ['described'],
				execute: ({ emit }) => {
					emit.described()
				},
			}),
	)
	.events(events => events.described({ description: 'The label was described' }))
	.done()

const blueprint = createWidgetSystem({ plugins: [labelled] })
	.createBlueprint({ id: 'w', type: 'labelled' })
if (blueprint.status !== 'valid')
	throw new Error('invalid')
const widget = blueprint.createRuntime()
	.getWidget('w')
if (widget === null)
	throw new Error('missing')

let described = 0
widget.events.described.subscribe(() => described++)
console.log(widget.properties.label.get()) // { ok: true, value: 'count 0' }
console.log(described) // 0: reading the Property emits nothing
widget.methods.announce()
console.log(described) // 1
```

### `transitivelyWrites === false` no longer means that a Method is read-only

Blueprint inspection gained `transitivelyEmits` on every Method member, beside `transitivelyWrites`. In
`0.0.x` a tool that offers the Methods a Property may depend on (an editor, a linter) filtered on
`transitivelyWrites === false`. A Method that emits has `transitivelyWrites === false` and is no longer a
valid dependency of a Property, so that filter now offers Methods the compiler rejects. Inspection does not
list which Events a Method declares in `emits`.

- **Detect:** silent. The filter keeps compiling and offers candidates that make the Blueprint `invalid`.
- **Find:** `transitivelyWrites`
- **Do:** require both facts: `!method.transitivelyWrites && !method.transitivelyEmits`. Across the Inspector
  protocol the field is `transitivelyEmits` on `InspectorMethodMember`, present from protocol 0.4 (see
  [Inspector protocol negotiation](#inspector-protocol-negotiation)); a peer negotiated below 0.4 does not
  receive it, so treat its absence as unknown, not as `false`.

### A throwing Property `compute` no longer breaks the writer

A Property whose `compute` throws no longer makes `state.set`, a Method call or `resetState()` throw,
and no longer stops other subscribers from being notified. Core reports the exception asynchronously
(a queued microtask); `get()` and dependency reads of that Property still rethrow synchronously.

- **Detect:** silent. A `try`/`catch` around a State write that used to catch a `compute` error never fires.
- **Find:** `try \{\n[^\n]*\.state\.\w+\.set\(` (multiline: `rg -U`)
- **Do:** read the Property (`get()`) or its diagnostics where you need the failure, and use a global
  error hook for the asynchronous report.

### Emit nesting is bounded

When one Runtime's `emit` calls nest more than 128 levels deep (a listener that keeps re-invoking the
Method that emitted), the next `emit` throws `WidgetSystemRuntimeReentrancyError` (a `RangeError`, `code`
`'emit-depth-exceeded'`, exported from the root). In `0.0.x` the loop ended in an engine
`RangeError: Maximum call stack size exceeded`. Method recursion that never ends still surfaces as a
`RangeError`, and no longer disables subscriptions in this or other Runtimes.

- **Detect:** run time only. **Find:** none; look for listeners that call Methods that emit
  (`events\.\w+\.subscribe\(`).
- **Do:** catch it as `error instanceof WidgetSystemRuntimeReentrancyError`, and remove the loop.

### Authored source and patch operands are bounded by `MAX_JSON_DEPTH`

Authored source and `SourcePatch` operands may nest at most `MAX_JSON_DEPTH` (256, exported)
containers. A widget node uses three containers per tree level (the node, `slots`, the slot array),
so that is about 85 levels of widgets. Deeper input is diagnosed (`json-incompatible-value` with reason
`max-depth-exceeded`, and `invalid-widget-definition` on the node where recovery stopped); a
`SourcePatch` path with more than `MAX_JSON_DEPTH + 2` segments fails with `max-depth-exceeded`. In
`0.0.x` this input could throw a `RangeError` from `createBlueprint`, `separateWidgetSource` and
`applyPatch`. Core never throws `RangeError` for deep or wide input now.

- **Detect:** a stored or generated document deeper than the limit is `invalid`.
- **Find:** none in code; compile the stored documents (see [Stored data](#stored-data)).
- **Do:** flatten the tree, or store fewer levels per document.

### `createBlueprintFromJson` equals `createBlueprint(JSON.parse(text))`

A JSON number literal that overflows (`1e400` parses to `Infinity`) used to produce a `valid`
Blueprint with `sourceJsonCompatible: true` while holding `Infinity`. It is now `json-incompatible-value`
with reason `non-finite-number`, the same as `createBlueprint(JSON.parse(text))`.

- **Detect:** silent; a document that "was valid" is now `invalid`. **Find:** `createBlueprintFromJson`.
- **Do:** fix the literal in the stored text.

### A structure validator that reports a location that does not exist throws

A slot, plugin or System `validateStructure` that reports an `index` outside the slot, a `slot` the
widget does not declare, or a node that is not part of the Blueprint being compiled now throws a
`TypeError` (an implementation bug in the validator) instead of producing a diagnostic with a dangling
location.

- **Detect:** a `TypeError` from `createBlueprint`. **Find:** `validateStructure`
- **Do:** report only locations that exist; check the `index` against `children.length`.

### Malformed plugin declarations throw when the plugin is built

The builder checks what it is given and throws a `TypeError` naming the plugin type, section, member
and field, instead of failing at the first use. It matters to untyped code (JavaScript, dynamic
loading, casts):

- a member must be declared with a definition object, and a section's required fields must be present
  and of the right kind (`validate`, `compute`, `validateArgs`, `execute`, `description`, ...);
- a section is sealed when its build callback returns: probing it (`JSON.stringify(section)`, template
  interpolation, `Promise.resolve(section)`) or declaring a member from a retained section throws;
- definitions are captured by value when declared, so changing a definition object afterwards has no effect;
- `.slots(definitions, validator)` with a second argument throws (use `.structure()`; see
  [Plugin builder](#plugin-builder)).

- **Detect:** a `TypeError` at plugin construction, which is module load for most libraries.
- **Find:** `\.slots\(` with a second argument (the pattern in [Plugin builder](#plugin-builder)); the
  other cases have no static pattern, so read the plugin modules that build sections dynamically.
- **Do:** remove the probe or the late declaration; declare members only inside the build callback.

### Frozen keyed surfaces in widget-vue

`useState()`, `useProperties()`, `useMethods()`, the three member-diagnostics accessors and `emit` return
a frozen, null-prototype object whose own enumerable keys are exactly the members the plugin declared.
`in`, `Object.keys` and spread are truthful. In `0.0.x` it was a Proxy for which `in` was `true` for any
string and `Object.keys` was empty. An undeclared name is `undefined` and absent from `in`; assigning
to a member or adding a property throws. `toRefs(surface)` is unsupported (members are already refs).

- **Detect:** silent for `in` and `Object.keys`; a `TypeError` on assignment in strict code.
- **Find:** `use(State|Properties|Methods|StateDiagnostics|PropertyDiagnostics|MethodDiagnostics)\(\)` lists the
  call sites; check what each result is used for (`toRefs`, `in`, assignment).
- **Do:** destructure the surface (`const { count } = useState()`).

### Inspector protocol negotiation

`INSPECTOR_PROTOCOL_VERSION` is `0.4` (it was `0.3`). Minors only add negotiated capabilities, and a peer
negotiated at an older minor sees exactly the previous wire shapes. Behavior that changes:

- **Only the handshake sets the negotiated minor.** In `0.0.x` any request could lower it for the
  whole session. Now another request is answered at the lower of the negotiated minor and its own
  envelope minor, without changing the session. A peer that never handshakes is served at the Agent's
  highest minor for events.
- **Errors are specific.** A well-formed request naming a method the protocol does not define is
  answered `unknown-method`, and a known method with invalid params `invalid-params` (both were
  `invalid-message`). Params validators ignore unknown extra fields.
- **DOM methods are advertised only when the Agent has a `dom` option.** `capabilities.methods` from the
  handshake no longer lists `inspect.*` / `highlight.*` for an Agent created without it, and those
  methods answer `unknown-method`.
- **0.4 adds** the `runtime.disposed` event, the `runtime-disposed` error, `authorWritable` on State
  members, `valueContractId` on Property members, `transitivelyEmits` on Method members and `keyTruncated`
  on object entries. A peer
  negotiated below 0.4 never sees them, and a peer at 0.4 or newer must accept them.
- **Values are bounded harder.** An encoded value has a total budget of `maxNodes` (1000), and object
  keys are cut at `maxStringLength` with `keyTruncated: true` (only for peers at 0.4 or newer).

- **Detect:** silent. **Find:** `INSPECTOR_PROTOCOL_VERSION|capabilities\.methods|'invalid-message'`
- **Do:** no change is needed unless your code relied on the `0.0.x` behavior above: a request that
  lowered the session's minor, `invalid-message` as the answer to an unknown method or invalid params,
  or `inspect.*` / `highlight.*` methods from an Agent created without a `dom` option. Adjust those as
  described in [`@deviltea/widget-inspector`](#widget-inspector). A peer that talks to a `0.4` Agent
  also handles the `0.4` additions listed there.

### Other behavior changes that need no code change

No change is needed for any of these, except where a bullet names one.

- `system.getPlugin(type)` returns `null` (not `undefined`) for an unregistered type. Search your code for
  `getPlugin`; a result compared with `=== undefined` must be compared with `=== null` or `== null`.
- `normalizeSeparatedWidgetSource` now carries `meta` from a flat entry (it dropped it before).
- The root diagnostics aggregate is incremental, and repeated `runtime.getDiagnostics()` returns the
  same cached snapshot while nothing changed.
- `createMessagePortChannelHub` (Inspector) buffers up to 64 messages per channel that arrive before
  the local side opens it, and at most 16 unopened channel names hold state.
- A long chain of Properties that read each other no longer ends in an engine `RangeError` when the
  Blueprint is compiled or the chain is read. Within one read a `compute` may now run more than once,
  which only matters if it is expensive or (against the contract) has side effects. Warming a long
  chain bottom-up is no longer needed. Unsubscribing from or disposing a long subscribed chain is
  still limited by the stack: see
  [Call-stack depth](../packages/widget-core#call-stack-depth).
- A Method invoked while another Runtime operation is in progress (from a listener, or from a Property
  through a declared dependency) no longer notifies its subscribers on its own: they are notified later
  in the same outermost operation, after the Method has returned and before the host's call into the
  Runtime returns. `0.0.6` could leave stale Property values and skip notifications when a Property
  depended on a Method and two or more subscribed Properties sat at or below it. What you can observe:
  - A Method invoked from a listener during another operation's flush now has its subscribers notified
    after the Method returns, later in the same operation. Before, that timing depended on whether the
    Method's diagnostics changed during the call; now it is uniform, and equal to `0.0.1`–`0.0.5`.
  - The order in which the listeners of one operation run can change.
  - Within one operation, the notifications and `compute` runs are those of `0.0.1`–`0.0.5`. Compared
    with `0.0.6`, a subscriber can now receive an intermediate value that `0.0.6` skipped, with one more
    `compute` run for it.
- Property inspection listeners (`inspectRuntime(runtime).getWidget(id).getProperty(name).subscribe()`)
  are notified once the Runtime call that caused the evaluation has finished, still before it returns,
  instead of in the middle of it. `getSnapshot()` is current as soon as the evaluation completes. A
  listener may now read Properties, write State and call Methods: before, doing so while Core was still
  evaluating could leave a Property out of date or make a subscriber miss a notification (issue #198).
  Within one call these listeners now run after the subscribers, diagnostics listeners and State
  inspection listeners; completions not delivered yet when the Runtime is disposed in the same call are
  dropped; and a listener that keeps changing what it observes is stopped after an internal number of
  rounds, with a reported `RangeError`. See
  [When Property inspection listeners run](../packages/widget-core#when-property-inspection-listeners-run).
- A `state.set()`, `runtime.resetState()` or `widget.resetState()` made while another Runtime operation is
  in progress (typically from a listener) no longer notifies its subscribers on its own either: they are
  notified later in the same outermost operation, after the write has returned and before the host's call
  into the Runtime returns. A write made with no operation in progress still notifies before it returns.
  `0.0.6` could miss a notification here: when a listener wrote a member and that member's listener wrote
  back what the first listener observes, the first subscriber was not told, for Property and State
  subscribers alike. What you can observe, compared with `0.0.6`:
  - The subscribers of such a write are always notified after it returns. In `0.0.6` they were usually
    notified during it, before the listener's `set()` or `resetState()` returned.
  - The order in which the listeners of one operation run can change.
  - A subscriber whose listener was still running when another subscription's listener wrote back what it
    observes is notified again, with the current value. A write-back made while the first listener is still
    running further up the stack is still not delivered to it: from an Event listener of an emit the first
    listener caused through a Method, from a State inspection listener of a write the first listener made,
    or when the host holds its own `alien-signals` batch around the write. See
    [Writing from a listener](../packages/widget-core#writing-from-a-listener).
  - Within one operation a subscriber can receive a different number of notifications: more (a value
    another listener wrote back, or a recompute that produced the value it already had) or fewer (the
    writes listeners make during one operation are combined, so a value that existed only between two of
    them is not delivered). A Property can be recomputed a different number of times.
  - A listener that writes the member it observes is still not guaranteed to be called again for its own
    write. It is now called again when anything reads that member later in the same operation (another
    subscriber, a subscribed Property that depends on it, or a plain `get()` from any listener), which
    `0.0.6` did not do in those cases.
  - If a listener writes and then disposes the Runtime in the same operation, the subscribers of that write
    are not notified. In `0.0.6` they were notified during the write.
  - Listeners that keep changing what they observe (a listener that writes a fresh sorted copy while
    something else reads the member, two listeners mirroring each other's objects, a diverging pair) keep
    running within one operation. In `0.0.6` they stopped after the first round and left a subscriber
    with an old value. Now a subscription's listener is called at most 100 times within one outermost
    operation (an internal limit that may change); beyond that it is not called again until that operation
    returns, and a `RangeError` naming the widget and member is reported the way a listener's exception is.
    The host's call returns normally and the next call counts from zero. The limit also stops the same
    loops written through Methods, which already looped with the Method change above. **Do:** write from a
    listener only when the contents actually differ (compare objects and arrays by their contents), and
    declare a Property for a value that must be derived or normalised instead of writing it back from a
    listener: a Property cannot loop, and a cycle between Properties is reported when the Blueprint is
    compiled (`property-evaluation-cycle`).

  Compared with `0.0.5`:
  - Property subscribers: when no listener writes what it observes, the notifications and their timing are
    those of `0.0.5`, which also delivered a listener's write after it returned and combined several writes
    to one member.
  - State subscribers: `0.0.5` notified them during the listener's `set()`, gave them every write (a
    listener that sets `b = 10` and then `b = 20` notified a State subscriber of `b` with `10` and `20`), and
    could miss a value written back to them. Now they are notified after the write returns, with the last
    value only (`20`), and are told about a value written back to them.
  - Loops: `0.0.5` already looped without end for Property subscribers and for writes through Methods; the
    limit now stops them.
  - A listener that writes what it observes is not guaranteed to be called again in either version, and
    the calls it gets can differ in either direction.

## Changes per package

### widget-core

#### Plugin builder

**`.slots(definitions, validator)` → `.slots(definitions).structure(validator)`.** The phase order is now
`description → interfaces → config? → slots? → structure? → state? → properties? → methods? → events? →
done`. `.structure(validateStructure)` is the plugin-level structure validator; it is optional and
available to every plugin, including one without slots, and it is not a capability. `.slots()` takes one
argument. The new type `WidgetPluginStructurePhase` is exported.

- **Detect:** compile error `TS2554: Expected 1 arguments, but got 2` on `.slots(...)`. In untyped code,
  a `TypeError` that says `takes only the slot definitions`.
- **Find:** `\.slots\(\s*(?:\w+|(?<a>\{(?:[^{}]|(?&a))*\}))\s*,(?!\s*\))` (multiline and recursive, so
  it needs the PCRE2 engine: `rg -P -U`). It matches a first argument that is an identifier or an object
  literal nested to any depth. A brace inside a string or regular expression in the first argument can
  unbalance it, and `tsc` reports every second argument anyway.
- **Do:** move the validator out of `.slots(...)` into `.structure(validator)`, chained right after it, as
  in the samples below.

**Asynchronous semantic callbacks are type errors.** A Method `execute` declared to return `void`
(or `unknown`, `{}`, `object`), and a slot, plugin or System `validateStructure`, that return a
`Promise` or any thenable are now rejected by the type-checker where they are written into the builder or
into `createWidgetSystem`'s options. They were already rejected at run time (a `TypeError`). Core is
synchronous: do the asynchronous work in the host and re-enter with a Method call.

- **Detect:** compile error `TS2322` on the callback (`Type 'Promise<void>' is not assignable to type
  'WidgetSynchronousResult<Promise<void>>'`), whose last line quotes `semantic callbacks are synchronous;
  returning a PromiseLike/thenable is a contract violation`.
- **Find:** `(execute|validateStructure)\s*[:(]\s*async\b|\basync\s+(execute|validateStructure)\s*\(` (the
  second branch is method shorthand, `async execute() {}`). It does not see a callback that is declared
  elsewhere and passed by name, or one that returns a Promise without being `async`; `tsc` reports
  those with the error above.
- **Do:** remove `async`, make the callback synchronous, and move the awaited work into the host, which
  calls a Method when the work finishes (see [Async work](../packages/widget-core#async-work)).

**A Method declares the Events it emits: `emits`.** In `0.0.x` every Method of a plugin that declared Events
received an `emit` with all of them, and nothing said which Method emits what. Now a Method lists the Events it
may emit in `emits`, and its `emit` carries only those. `emit.name(...)` is still how it emits, and an
Event's argument tuple is still typed. That is what lets the compiler tell a Method that emits from a read-only
one (see [A Property cannot depend on a Method that emits](#a-property-cannot-depend-on-a-method-that-emits)).
Also compared with `0.0.6`:

- A Method without `emits` (or with `emits: []`) emits nothing, and its `emit` has no own members. The name of
  each Event of the plugin is still present on it (`'change' in emit` is `true`) and calling it throws a
  `TypeError`, so do not write `emit.change?.()` expecting a no-op.
- A Method that emits only through another Method it invokes declares nothing: the emit belongs to the Method
  that calls `emit`.
- `emits` is checked when the plugin is built. A value that is not an array of strings (including an array with a
  hole) throws a `TypeError` from the member call inside `.methods(...)`, naming the plugin and the Method but no
  Event. A name that is not declared in the `events` section, or a name listed twice, throws a `TypeError` from
  `done()` that names the plugin, the Method and the Event. In a plugin without an `events` section `emits: []` is
  accepted and any name is rejected.
- An Event a Method did not list throws a `TypeError` that names the Method and the Event when the Method emits
  it (untyped code and casts); nothing is delivered, and no listener runs. Such a callable is a `TypeError`
  before and after `runtime.dispose()`, never `WidgetSystemRuntimeDisposedError`. When the running Method did list
  the Event, the callable is another Method's, and the error is the closed-callable `TypeError` that does not name
  the running Method.
- An `emit` is closed like the `deps` callables: it works only while its own Method's callback is the innermost
  running callback, so one retained by a Method does not work while a different Method of the same widget
  runs. In `0.0.6` it worked.

- **Detect:** a compile error where `emit.x(...)` is called in a Method that does not list `x`: `TS2339:
  Property 'x' does not exist on type 'WidgetMethodEventEmitter<..., never>'` (the last type argument is the
  union of the Events the Method lists, `never` when it lists none). The same error appears in an `execute` whose
  context parameter you annotated (see **Do**). In untyped code, the `TypeError` above at the first `emit`.
- **Find:** `\bemit\b` in the `execute` callbacks of plugins that declare `events`, for example
  `rg -nP '\bemit\b' -g '*.{ts,vue,js}' .`. `tsc` reports every typed site; only code that reaches `emit`
  through a cast or an untyped plugin needs this search.
- **Do:** add `emits: [...]` to each Method that calls `emit`, listing every Event it emits itself. A Method that
  keeps `emit` in a variable lists every Event it calls; `emit` cannot be handed to another Method (a Method that
  receives it throws, whatever it declares): only a plain function that the Method calls synchronously, from inside
  its own `execute`, can use it. Leave a Method that does
  not emit without `emits`. A standalone `WidgetMethodDefinition<Interfaces, Name, Deps, Result>` annotation
  takes the declaration as a fifth type argument (`..., 'change'`) to emit, and `emits: [...]` must then be written
  too: the type requires it. Write `emits` as a literal array: a variable typed as an array of every Event name
  gives `emit` every Event, while the list the runtime checks may be narrower. An `execute` whose context parameter
  you annotated, `(ctx: WidgetMethodExecuteContext<Interfaces, Name, Deps>)`, now has an `emit` without members
  even when `emits: ['change']` is written (`TS2339`), because the annotation fixes the new trailing `Emits`
  type parameter, which defaults to `never`, to `never`: pass the Events as the trailing argument
  (`WidgetMethodExecuteContext<Interfaces, Name, Deps, 'change'>`), or drop the annotation and let the builder
  infer it. `WidgetEventEmitterContext<Interfaces>` changed the same way. The type of the `emit` argument is
  `WidgetMethodEventEmitter<Interfaces, Emits>` (new export); `WidgetEventEmitter<Interfaces>` keeps meaning
  all Events of a plugin.

## Stored data

Core does not version or migrate documents. These changes can make a source that was valid under
`0.0.x` invalid under `0.1`:

1. **An extra key on a widget node** (anything but `id`, `type`, `config`, `slots`, `meta`):
   `unexpected-widget-field`. Move the value under `meta`.
2. **Nesting deeper than `MAX_JSON_DEPTH`** (256 containers, about 85 widget levels): `json-incompatible-value`
   with reason `max-depth-exceeded`.
3. **A JSON number literal that overflows** (`1e400`) in text loaded with `createBlueprintFromJson`:
   `json-incompatible-value` with reason `non-finite-number`.
4. **A plugin you changed** while upgrading (a removed type, a config shape, a Method that now declares `emits`
   while a Property depends on it): the same loop as before; see
   [Persisted documents](../packages/widget-core#persisted-documents) for the repair loop.

Validity is all-or-nothing: a document with any diagnostic creates no Runtime, and Core does not run part of
it. A host that must stay usable while a stored or edited document is invalid (an editor, a live preview)
keeps its last valid Runtime and shows the diagnostics next to it; see
[Editing a document that is currently invalid](../packages/widget-core#editing-a-document-that-is-currently-invalid).

State is not part of a source. `runtime.snapshotState()` returns the current State in the shape
`createRuntime({ overrideStateDefaults })` accepts, which is how you carry State across a recompile.

Patches you stored (a log of `SourcePatch` arrays) replay the same way, but a patch that was malformed now fails
with `invalid-operation` where it failed with `invalid-path`.

Separated sources (`{ structure, widgets }`) keep their shape. `normalizeSeparatedWidgetSource` now keeps `meta`
on a flat entry; produce them with the new `separateWidgetSource`, which reports what it could not project.

This runnable script audits stored documents against the new rules and moves extra keys under `meta` with a
`SourcePatch`, one diagnostic at a time (the stored input is never mutated, because patches are
copy-on-write). Replace the plugin with your System. A key that already exists inside `meta`, or a `meta` that is
not an object, fails the patch and is left for a person to resolve.

<!-- sample: stored-migrate-meta run -->
```ts

	.description('A note widget')
	.interfaces<Record<never, never>>()
	.done()
const system = createWidgetSystem({ plugins: [note] })

function valueAt(source: unknown, path: readonly (string | number)[]): unknown {
	let current = source
	for (const segment of path)
		current = (current as Record<string | number, unknown>)[segment]
	return current
}

/** Moves every unexpected widget key under `meta`; returns the repaired source. */
function moveExtraKeysToMeta(stored: unknown): unknown {
	const document = createWidgetDocument({ system, source: stored })
	for (let pass = 0; pass < 1000; pass++) {
		const { blueprint } = document.getSnapshot()
		let moved = false
		for (const diagnostic of blueprint.diagnostics) {
			if (diagnostic.code !== 'unexpected-widget-field')
				continue
			const base = blueprint.getSourcePath(diagnostic.location.node)
			const key = diagnostic.path[0]
			if (base === null || typeof key !== 'string')
				break
			const node = valueAt(blueprint.source, base) as { meta?: unknown }
			const patch = [
				...(node.meta === undefined ? [{ op: 'add' as const, path: [...base, 'meta'], value: {} }] : []),
				{ op: 'move' as const, from: [...base, key], path: [...base, 'meta', key] },
			]
			moved = document.applyPatch(patch).ok
			break
		}
		if (!moved)
			break
	}
	return document.getSnapshot().blueprint.source
}

const stored = { id: 'note-1', type: 'note', label: 'Hello' }
const repaired = moveExtraKeysToMeta(stored)
console.log(JSON.stringify(repaired)) // {"id":"note-1","type":"note","meta":{"label":"Hello"}}
console.log(system.createBlueprint(repaired).status) // valid
console.log(JSON.stringify(stored)) // unchanged
```

## New API worth adopting

- `runtime.snapshotState()`: current State as a plain object that `overrideStateDefaults` accepts. See
  [Snapshotting state](../packages/widget-core#snapshotting-state-snapshotstate).
- `RuntimeWidget.resetState()`: reset one widget's State to its initialization outcome. See
  [Reusing a Runtime](../packages/widget-core#reusing-a-runtime-resetstate).
- `blueprint.getSourcePath(node)` and inspection `sourcePath`: the path of a node inside the source, usable
  verbatim in a `SourcePatch`. See [Compiling a blueprint](../packages/widget-core#compilation-boundary-and-recovery).
- The `.structure()` phase: a plugin-level structure validator for every plugin. See
  [Structure validation](../packages/widget-core#structure-validation).
- `runtime.subscribeDisposal(listener)`: runs the listener once, synchronously, inside the first
  `runtime.dispose()`, so a host can cancel the asynchronous work it owns (a request, a timer, a worker). The
  Runtime is already fully disposed when the listener runs, so the listener cannot read or write it; a
  throwing listener does not reach the `dispose()` caller. It returns an idempotent unsubscribe function, and
  it throws `WidgetSystemRuntimeDisposedError` on a Runtime that is already disposed (check
  `runtime.isDisposed` first). See [Disposal](../packages/widget-core#disposal) and
  [Async work](../packages/widget-core#async-work).
- `useWidget().config`: the widget's resolved config, read-only. See
  [Config](../packages/widget-vue#config).
- The scoped `WidgetSlot` default slot (`{ Child, id, type, index }`): wrap, decorate or skip children. See
  [Scoped slot](../packages/widget-vue#scoped-slot).
- `@deviltea/widget-vue/testing` (`createWidgetTestHost`): test one renderer against a real Runtime. See
  [Testing a renderer](../packages/widget-vue#testing-a-renderer).
- The Inspector client `requestTimeoutMs` and the Agent `valueLimits`. See
  [`@deviltea/widget-inspector`](../packages/widget-inspector).
- Also: `isJsonValue`, `MAX_JSON_DEPTH`, `createWidgetDocument`'s `{ previous, patch }` listener argument and
  `assertCoreRuntime` from `@deviltea/widget-core/integration`.

## Upgrade checklist

1. Run `pnpm why @deviltea/widget-core` (or your package manager's equivalent). Resolve to one version before
   changing anything else.
2. Raise `@deviltea/widget-core` to `^0.1.0`, then `@deviltea/widget-vue` and
   `@deviltea/widget-inspector` to `^0.1.0`. In every plugin library and renderer library, move Core to
   `peerDependencies` and `devDependencies`, and mark it external in the bundler. Use Node `>=22.14.0`.
3. Run the **Find** patterns of the [silent changes](#changes-that-will-not-show-up-as-a-compile-error) and
   fix every match, starting with `RuntimeDiagnostic`, Event listeners, `deps`/`emit` callables and extra keys.
4. Rename the exported names ([table](#exported-names-and-types)): `WidgetSystemRuntimeDiagnostic`,
   `RuntimeDiagnostic`, `RuntimeDiagnosticLocation`, `Diagnostic`, `ValidBlueprintView`, `widget.blueprint`.
5. Move the plugin-level validator from `.slots(definitions, validator)` to `.structure(validator)`, and remove
   `async` from `execute` and `validateStructure` callbacks. Add `emits` to every Method that calls `emit`, then
   look at every Property that depends on a Method: it may depend only on a Method that neither writes State nor
   emits.
6. Update code that switches on codes (`duplicate-widget-id`, SourcePatch failures, `invalid-options`,
   Vue and Inspector codes), and the call sites of `separateWidgetSource`, `system.getPlugin` and
   `WidgetSystemConfigurationError.pluginIndex`.
7. Run the type-check (`tsc --noEmit`). A remaining error is one of: a removed or renamed name (step 4), an
   arity or return type that changed (step 5 or 6), or a type you derived from a widened union
   (`RuntimeDiagnostic`, a code union): handle the new members.
8. Compile every stored document and list the diagnostics. Repair `unexpected-widget-field` (the
   [script](#stored-data) above), then anything about depth or `1e400`. A diagnostic you do not expect is a
   plugin that changed, not an upgrade problem.
9. Run the tests. A failure that says `TypeError` at a `deps.*` or `emit.*` call is step 3 (callback
   lifetime) or, when the message says the Method emitted an Event without declaring it, step 5 (`emits`);
   a Blueprint that is `invalid` with `property-dependency-has-side-effects` is step 5 (a Property depends on a
   Method that emits or writes State); `foreign-runtime` is step 1; a throw while building a plugin is the sealed-section rule; a test
   that expected an Event listener's exception to reach the Method caller needs the listener or a global
   error hook to assert it.
10. For Vue, run a mount of every renderer and `pnpm why vue @deviltea/widget-core`. For the Inspector, run a
    handshake and read `capabilities`; handle the `runtime.disposed` event and the new error codes.
