# Migrating from 0.3 to 0.4

This page takes a plugin library, an application or a renderer library from the `0.3` line to `0.4`. While the
packages are `0.x`, a breaking change in any package bumps the minor version of all of them
(`@deviltea/widget-core`, `@deviltea/widget-inspector`, `@deviltea/widget-vue`, and from `0.4.0` the newly published
`@deviltea/widget-docs-generator`).

In `0.3` a plugin's prose was JSDoc on its `Interfaces` type, read by a documentation generator. In `0.4` the prose is
written in the plugin builder again, beside each definition, and the compiler requires it to be complete: every
declared type is documented down to its inner fields. The `Interfaces` type stays the single source of the shape,
and a JSON Schema is still inferred from the types by tooling outside Core; it now states the shape only. Core keeps
the prose as plain data on `plugin.docs` and never reads it. The decision is recorded in
[Discussion #12](https://github.com/DevilTea/widget/discussions/12#discussioncomment-19850339), "Descriptions live in
the plugin builder; JSON Schema is inferred from the types (0.4.0)".

Each entry follows the shape of [Migrating from 0.0.x to 0.1](./0.1): **Detect** says how the change shows itself,
**Find** gives a search that locates the affected code, and **Do** says what to change.

## Before you start: install and versions

Upgrade all the Widget packages you use in one change, to the `0.4` line:

```bash
pnpm add @deviltea/widget-core@^0.4.0
pnpm add @deviltea/widget-vue@^0.4.0 @deviltea/widget-inspector@^0.4.0 # only the ones you use
pnpm add -D @deviltea/widget-docs-generator@^0.4.0 # if you generate docs, schemas or skills
```

A dependent at `0.4.0` declares Core as `^0.4.0` (`>=0.4.0 <0.5.0`), so a `0.3.x` Core no longer satisfies its peer
range: upgrade Core together with the dependents.

## Who needs to do what

| You are | Do |
| --- | --- |
| A plugin author | Every entry under [Plugin builder](#plugin-builder), then [Field docs](#field-docs). Move each JSDoc comment of your `Interfaces` type into the builder |
| A plugin library that builds plugins with a factory | Also [Plugin factories](#plugin-factories) |
| A plugin author who used `@widgetRef` or a constraint tag (`@minimum`, `@pattern`, ...) | [`WidgetRef` replaces `@widgetRef`](#widgetref-replaces-widgetref) and [Constraint tags are retired](#constraint-tags-are-retired) |
| A tool that reads a plugin's prose | [`plugin.docs`](#plugin-docs) and [JSDoc is no longer read](#jsdoc-is-no-longer-read) |
| A project that copied or ran the repository's private `@deviltea/widget-skills` generator | [The generator is published](#the-generator-is-published) |
| A project that installed the generated `widget-plugin-authoring` skill | [Agent Skills ship with the packages](#agent-skills) |
| A host that reads `inspectPlugin(plugin).events` or the Events of a Blueprint inspection, and declares an Event whose name is an integer (`'2'`) | [Event order follows JavaScript key order](#event-order-follows-javascript-key-order) |
| A host that connects an Inspector client to an Agent | [Inspector](#inspector): nothing changes; the protocol stays `1.0` |
| A renderer author using `@deviltea/widget-vue` | [Vue adapter](#vue-adapter): nothing changes |

Every breaking change to the Core API in this page is a compile error in TypeScript. The Event order is a run-time
change without a compile error, and the tooling changes (JSDoc, `@widgetRef` and the constraint tags are no longer
read) show only in the generated documentation and schemas. In JavaScript, or in a module loaded without type-checking, a `0.3` plugin definition
throws a `TypeError` when the plugin is built; see [Run-time checks of the docs](#run-time-checks-of-the-docs).

## Plugin builder

The phase order is now:

```text
description -> interfaces -> config? -> slots? -> structure? -> state? -> properties? -> methods? -> events? -> reasons? -> done
```

A description is Markdown prose. Wherever one is required you may write `undocumented` instead (see
[`undocumented`](#undocumented)); everywhere else on this page, the samples write the prose.

### `.description(text)` is the first phase

The builder starts with `.description(text)` again. `createWidgetPlugin(type)` returns
`WidgetPluginDescriptionPhase<Type>` (it returned `WidgetPluginInterfacesPhase<Type>` in `0.3`); `.interfaces()` is
the second phase.

- **Detect:** `This expression is not callable. Type 'WidgetPluginPhaseOrderViolation<"'.interfaces()' is called too
  early; call '.description()' first. ...">' has no call signatures` at each `.interfaces<...>()` call. In
  JavaScript, `.interfaces()` throws a `TypeError` that names the plugin.
- **Find:** `rg "createWidgetPlugin\("`.
- **Do:** insert `.description(text)` before `.interfaces()`, with the text of the JSDoc comment on the interfaces
  type. Where a type named the builder's first phase, use `WidgetPluginDescriptionPhase<Type>`.

Every slot definition requires `description` as well. A slot has no value of its own, so the description is all it
takes.

<!-- sample: plugin-description-before before -->
```ts
import type { WidgetChild } from '@deviltea/widget-core'
import { createWidgetPlugin } from '@deviltea/widget-core'

/** A titled container. */
interface PanelInterfaces {
	slots: {
		/** The widgets the panel lays out. */
		content: WidgetChild
	}
}

export const panel = createWidgetPlugin('panel')
	.interfaces<PanelInterfaces>()
	.slots({ content: {} })
	.done()
```

<!-- sample: plugin-description-after run -->
```ts
import type { WidgetChild } from '@deviltea/widget-core'
import { createWidgetPlugin } from '@deviltea/widget-core'

interface PanelInterfaces {
	slots: { content: WidgetChild }
}

export const panel = createWidgetPlugin('panel')
	.description('A titled container.')
	.interfaces<PanelInterfaces>()
	.slots({ content: { description: 'The widgets the panel lays out.' } })
	.done()

console.log(panel.docs.description) // A titled container.
console.log(panel.docs.slots?.content) // { description: 'The widgets the panel lays out.' }
```

### `.config()` takes `description`, `raw` and `resolved`

The config definition is `{ description, raw, resolved, validate, resolve }`. `raw` documents
`Interfaces['config']['raw']` and `resolved` documents `Interfaces['config']['resolved']`, each as field docs (see
[Field docs](#field-docs)): for an object type, a `fields` entry for every key. `null` is ignored, so a raw config
typed `Raw | null` is documented as `Raw`. `raw` and `resolved` are required when the description is prose, and
optional when it is `undocumented`.

- **Detect:** `Property 'description' is missing in type '{ validate: ...; resolve: ...; }'` at the `.config({`
  argument; once `description` is written, `... is missing the following properties from type ...: raw, resolved`.
- **Find:** `rg "\.config\(\{"`.
- **Do:** move the JSDoc of the `config` member into `description`, and the JSDoc of each field of the raw and
  resolved types into `raw.fields` and `resolved.fields`.

<!-- sample: config-docs-before before -->
```ts
import { createWidgetPlugin } from '@deviltea/widget-core'

interface BadgeInterfaces {
	/** How the badge is labelled. */
	config: {
		raw: {
			/** The text shown on the badge. Defaults to "Badge". */
			label?: string
		} | null
		resolved: {
			/** The text shown on the badge. */
			label: string
		}
	}
}

export const badge = createWidgetPlugin('badge')
	.interfaces<BadgeInterfaces>()
	.config({
		validate: (input): input is { label?: string } | null => input === null || typeof input === 'object',
		resolve: raw => ({ label: raw?.label ?? 'Badge' }),
	})
	.done()
```

<!-- sample: config-docs-after run -->
```ts
import { createWidgetPlugin } from '@deviltea/widget-core'

interface BadgeInterfaces {
	config: {
		raw: { label?: string } | null
		resolved: { label: string }
	}
}

export const badge = createWidgetPlugin('badge')
	.description('A short label.')
	.interfaces<BadgeInterfaces>()
	.config({
		description: 'How the badge is labelled.',
		raw: { fields: { label: { description: 'The text shown on the badge. Defaults to "Badge".' } } },
		resolved: { fields: { label: { description: 'The text shown on the badge.' } } },
		validate: (input): input is { label?: string } | null => input === null || typeof input === 'object',
		resolve: raw => ({ label: raw?.label ?? 'Badge' }),
	})
	.done()

console.log(JSON.stringify(badge.docs.config?.raw))
// {"fields":{"label":{"description":"The text shown on the badge. Defaults to \"Badge\"."}}}
```

A `0.2`-shaped config definition, with `fields` (or `items`, `values`, `ref`) at its top, is a type error and throws
a `TypeError` at run time that says the docs go under `raw` and `resolved`.

### State and Properties take `description` and the docs of their value

Each State member and each Property takes `description`, plus the field docs of its value type when that type has
inner fields: `fields` for an object, `items` for an array of objects, `values` for a dictionary of objects (see
[Field docs](#field-docs)). A value of a primitive type takes the description only.

- **Detect:** `Property 'description' is missing in type '{ validate: ...; }' but required in type '{ readonly
  description: string; }'` at a State or Property definition; then, for a value with inner fields, `Property 'items'
  is missing` (or `'fields'`, `'values'`).
- **Find:** `rg "\.state\(|\.properties\("`.
- **Do:** move the JSDoc of the member into `description`, and the JSDoc of the inner fields of its value type into
  the nested docs.

<!-- sample: value-docs-before before -->
```ts
import { createWidgetPlugin } from '@deviltea/widget-core'

/** One line of the cart. */
interface CartLine {
	/** The product's stock-keeping unit. */
	sku: string
	/** How many items of the product. */
	quantity: number
}

interface CartInterfaces {
	state: {
		/** The lines, in the order they were added. */
		lines: readonly CartLine[]
	}
	properties: {
		/** The number of items in every line together. */
		count: number
	}
}

export const cart = createWidgetPlugin('cart')
	.interfaces<CartInterfaces>()
	.state(state => state.lines({
		validate: (input): input is readonly CartLine[] => Array.isArray(input),
		default: () => [],
	}))
	.properties(properties => properties.count({
		registerDeps: ({ dep }) => ({ lines: dep.self.state.get('lines') }),
		compute: ({ deps }) => {
			const lines = deps.lines()
			return lines.ok ? (lines.value ?? []).reduce((sum, line) => sum + line.quantity, 0) : 0
		},
	}))
	.done()
```

<!-- sample: value-docs-after run -->

### Methods take `description`, `params` and `returns`

A Method definition takes `description`, `params` and `returns`. `params` has one entry per parameter, **by
position**: TypeScript does not expose the labels of a parameter tuple to the type system, so the entries cannot be
keyed by name. Each entry is a description plus the field docs of the parameter's type, and so is `returns`.

- `params` may be left out when the Method takes no parameter. A rest parameter needs at least one entry, after one
  entry per fixed parameter: `(...lines: string[])` takes one entry or more.
- `returns` is not written when the Method returns no value: `void`, `undefined`, `void | undefined` or `never`. It is
  required for any other return type, `unknown` and `any` included.

- **Detect:** `Property 'description' is missing`, then `Property 'params' is missing` or `Property 'returns' is
  missing`, at the Method definition.
- **Find:** `rg "\.methods\("`.
- **Do:** move the JSDoc of the Method into `description`, each `@param` into its `params` entry in parameter order,
  and `@returns` into `returns`.

<!-- sample: method-docs-before before -->
```ts
import { createWidgetPlugin } from '@deviltea/widget-core'

interface StockInterfaces {
	state: { quantity: number }
	methods: {
		/**
		 * Adds items to the stock.
		 * @param amount How many items to add.
		 * @returns The new quantity.
		 */
		add: (amount: number) => number
		/** Empties the stock. */
		clear: () => void
	}
}

export const stock = createWidgetPlugin('stock')
	.interfaces<StockInterfaces>()
	.state(state => state.quantity({ validate: (input): input is number => typeof input === 'number', default: () => 0 }))
	.methods(methods => methods
		.add({
			validateArgs: (args): args is [number] => args.length === 1 && typeof args[0] === 'number',
			registerDeps: ({ dep }) => ({ quantity: dep.self.state.get('quantity'), setQuantity: dep.self.state.set('quantity') }),
			execute: ({ args: [amount], deps }) => {
				const current = deps.quantity()
				const next = (current.ok ? current.value ?? 0 : 0) + amount
				deps.setQuantity(next)
				return next
			},
		})
		.clear({
			validateArgs: (args): args is [] => args.length === 0,
			registerDeps: ({ dep }) => ({ setQuantity: dep.self.state.set('quantity') }),
			execute: ({ deps }) => {
				deps.setQuantity(0)
			},
		}))
	.done()
```

<!-- sample: method-docs-after run -->

### `.events()` takes one docs entry per Event

`.events(names)` took the list of Event names. `.events(definitions)` takes a record keyed by Event name, with one
entry for every key of `Interfaces['events']`: `{ description, payload }`, where `payload` documents the payload
positions the way `params` documents a Method's parameters. `payload` may be left out for an Event without a
payload. `.events({})` declares an explicitly empty capability. A missing name and a name the interfaces do not
declare are type errors, also when the record arrives through a variable.

`ExactWidgetEventNames`, `WidgetEventNamesViolation` and `WidgetEventNamesTupleViolation` are removed;
`WidgetEventDefinitions` types the record, and an undeclared name shows as `WidgetUndeclaredMemberViolation<'events'>`.

- **Detect:** `Type 'string' is not assignable to type 'WidgetUndeclaredMemberViolation<"events">'` on each entry of
  the list. In JavaScript, a list throws a `TypeError`: the section must be a plain object of docs keyed by name.
- **Find:** `rg "\.events\(\["`.
- **Do:** turn the list into a record and move the JSDoc of each Event into its entry, and the JSDoc of its payload
  into `payload`.

<!-- sample: events-record-before before -->
```ts
import { createWidgetPlugin } from '@deviltea/widget-core'

interface ButtonInterfaces {
	events: {
		/** The button was pressed. */
		pressed: []
		/** The label changed. */
		changed: [label: string]
	}
}

export const button = createWidgetPlugin('button')
	.interfaces<ButtonInterfaces>()
	.events(['pressed', 'changed'])
	.done()
```

<!-- sample: events-record-after run -->
```ts
import { createWidgetPlugin } from '@deviltea/widget-core'

interface ButtonInterfaces {
	events: {
		pressed: []
		changed: [label: string]
	}
}

export const button = createWidgetPlugin('button')
	.description('A button with a label.')
	.interfaces<ButtonInterfaces>()
	.events({
		pressed: { description: 'The button was pressed.' },
		changed: { description: 'The label changed.', payload: [{ description: 'The new label.' }] },
	})
	.done()

console.log(JSON.stringify(button.docs.events))
// {"pressed":{"description":"The button was pressed."},"changed":{"description":"The label changed.","payload":[{"description":"The new label."}]}}
```

#### Event order follows JavaScript key order

The Events a plugin declares are the keys of the record, in JavaScript key order. That is declaration order, except
that integer-like names (`'2'`, `'10'`) come first, in ascending order, as in any JavaScript object. In `0.3` the
order was the order of the list. It shows wherever the Events are listed: `inspectPlugin(plugin).events`, the
Events of a Blueprint inspection, the Inspector's Event members and `plugin.docs.events`.

- **Detect:** an Event named like an integer moves to the front of those lists.
- **Find:** `rg "\.events\(\{"` and look for quoted integer keys.
- **Do:** nothing, unless your code depends on the position: then sort by name, or rename the Event.

<!-- sample: event-order run -->
```ts
import { createWidgetPlugin, undocumented } from '@deviltea/widget-core'
import { inspectPlugin } from '@deviltea/widget-core/inspection'

const pager = createWidgetPlugin('pager')
	.description('A pager.')
	.interfaces<{ events: { 'page-changed': [], '10': [], '2': [] } }>()
	.events({ 'page-changed': undocumented, '10': undocumented, '2': undocumented })
	.done()

console.log([...inspectPlugin(pager).events?.keys() ?? []]) // [ '2', '10', 'page-changed' ]
```

### `.reasons()` is a new phase

When the interfaces declare `Interfaces['reasons']`, the builder has a `.reasons(definitions)` phase after
`.events()`, and it is required: `.done()` is not available until it is called. It takes one entry for every reason,
keyed by name: `{ description, details }`. `details` is the field docs of the reason's payload: required when the
payload is not `void`, and a type error when it is. `.reasons()` records docs only; `reasons` is still not a
capability.

- **Detect:** `Property 'done' does not exist on type 'WidgetPluginReasonsPhaseMembers<...>'` on a plugin that
  declares `reasons`.
- **Find:** `rg "reasons:"` in your interfaces types.
- **Do:** call `.reasons({...})` last, with the JSDoc of each reason and of its payload's fields.

<!-- sample: reasons-docs-before before -->
```ts
import { createWidgetPlugin } from '@deviltea/widget-core'

interface GaugeInterfaces {
	state: { level: number }
	reasons: {
		/** The value is not a number. */
		'not-a-number': void
		/** The value is above the gauge's maximum. */
		'too-large': {
			/** The largest accepted value. */
			max: number
			/** The value that was rejected. */
			received: number
		}
	}
}

export const gauge = createWidgetPlugin('gauge')
	.interfaces<GaugeInterfaces>()
	.state(state => state.level({
		validate: (input, ctx): input is number => {
			if (typeof input !== 'number') {
				ctx.addDiagnostic({ message: 'The level must be a number.', reason: 'not-a-number' })
				return false
			}
			if (input > 100) {
				ctx.addDiagnostic({ message: 'The level is too large.', reason: 'too-large', details: { max: 100, received: input } })
				return false
			}
			return true
		},
		default: () => 0,
	}))
	.done()
```

<!-- sample: reasons-docs-after run -->
```ts
import { createWidgetPlugin } from '@deviltea/widget-core'

```

## Field docs

### What `FieldDocs` requires

The docs of a value of type `T` are complete when the compiler accepts them. `FieldDocs<T>` (and `FieldDoc<T>`, the
same with a required description) asks for:

| `T` | Nested docs |
| --- | --- |
| an object type | `fields`, with an entry for every key, optional keys included |
| a union of object types | `fields`, with an entry for every key that appears in any member; a key several members share has one entry |
| an array (`T[]`, `readonly T[]`) | `items`, the docs of the element; required when the element has inner fields, optional otherwise |
| a dictionary (`Record<string, T>`, an index signature) | `values`, the docs of the values; required when the values have inner fields, optional otherwise |
| a primitive, a literal union, a function, `unknown`, `any`, a `WidgetRef` | nothing beyond the description |
| a built-in object: `Date`, `RegExp`, `Map`, `Set` and their read-only and weak forms, `Promise`, `Error`, `ArrayBuffer`, `DataView`, the typed arrays | nothing beyond the description |

A class of your own is an ordinary object type: its fields are documented. `null` and `undefined` are ignored
(`X | null` is documented as `X`), and the parts of a union combine: `boolean | Condition` needs the `fields` of
`Condition`. Each entry in `fields` is itself a description plus the nested docs of its own type, so the docs follow
the type down to its leaves. A key that `T` does not have is a type error in a docs object literal written in place.

An entry whose description is `undocumented` may leave its nested docs out (see [`undocumented`](#undocumented)).

<!-- sample: field-docs-rules run -->
```ts
import { defineFieldDocs } from '@deviltea/widget-core'

interface Schedule {
	title: string
	startsAt: Date
	note?: string | null
	reminder: { kind: 'email', address: string } | { kind: 'push' }
	slots: readonly { day: string, hours: number }[]
	tags: readonly string[]
	owners: Record<string, { name: string }>
}

const scheduleDocs = defineFieldDocs<Schedule>()({
	fields: {
		title: { description: 'The schedule\'s name.' },
		startsAt: { description: 'When the first slot starts.' },
		note: { description: 'A remark shown under the title; none when `null` or omitted.' },
		reminder: {
			description: 'How the attendees are reminded.',
			// Every key of every member: `kind` once, `address` from the email member.
			fields: {
				kind: { description: 'The channel.' },
				address: { description: 'The address to write to, for an email reminder.' },
			},
		},
		slots: {
			description: 'The weekly slots.',
			items: { fields: { day: { description: 'The day of the week.' }, hours: { description: 'How long the slot is.' } } },
		},
		// An array of strings: `items` is optional.
		tags: { description: 'Free-form labels.' },
		owners: {
			description: 'The people who may edit the schedule, by user id.',
			values: { fields: { name: { description: 'The name shown to others.' } } },
		},
	},
})

console.log(Object.keys(scheduleDocs.fields)) // [ 'title', 'startsAt', 'note', 'reminder', 'slots', 'tags', 'owners' ]
```

### `defineFieldDocs` checks spreads and variables

The builder sections and `defineTypeDocs` get TypeScript's excess-property check, which applies to an object literal
written in place. A key that reaches the docs through a spread or through a variable is not checked there: a stale
entry, left behind after a field was renamed, still compiles. `defineFieldDocs<T>()(docs)` checks a docs value
against `T` at every depth, spreads and variables included, and returns it unchanged. Use it wherever docs are
assembled from parts or written apart from the builder.

<!-- sample: define-field-docs after -->
```ts
import { defineFieldDocs } from '@deviltea/widget-core'

interface TextRaw {
	placeholder?: string
	maxLength?: number
}

interface ShortAnswerRaw extends TextRaw {
	format?: 'text' | 'email'
}

const textDocs = defineFieldDocs<TextRaw>()({
	fields: {
		placeholder: { description: 'The hint shown in an empty field.' },
		maxLength: { description: 'The longest answer, in characters; no limit when omitted.' },
	},
})

export const shortAnswerDocs = defineFieldDocs<ShortAnswerRaw>()({
	fields: { ...textDocs.fields, format: { description: 'The input format; text when omitted.' } },
})

export const staleDocs = defineFieldDocs<TextRaw>()({
	// @ts-expect-error `format` is not a field of `TextRaw`, although it arrives through a spread
	fields: { ...shortAnswerDocs.fields },
})
```

### Shared types: `defineTypeDocs` and `ref`

A named type used in several places is documented once with `defineTypeDocs<T>(name, docs)`: a description plus
the inline nested docs of `T`. A field of that type refers to it with `ref` instead of writing `fields`, `items` or
`values`; `ref` and inline docs exclude each other. A `ref` must name docs of exactly the field's object type. A
recursive type refers to itself with a thunk, `ref: () => conditionDocs`, because a constant cannot name itself in
its own initializer; such a declaration needs an explicit annotation, `const conditionDocs: TypeDocs<Condition> = …`,
or TypeScript reports TS7022 (the constant implicitly has type `any`).

`name` is the name tooling gives the type (one JSON Schema `$defs` entry). Within one plugin, two different type
docs may not share a name: `done()` throws a `TypeError`. `plugin.docs` keeps each `ref` as that name and lists the
referenced type docs under `types`.

- **Detect:** `Property 'fields' is missing` (or `'items'`, `'values'`) at each place that uses the type: JSDoc on the
  type is no longer read, so its docs are required where it is used.
- **Find:** the named types your configs and values use.
- **Do:** declare the type docs once and `ref` them.

<!-- sample: type-docs-before before -->
```ts
/** A rule over the answers. */
export type Condition
	= | {
		/** The kind of rule. */
		op: 'all'
		/** Every rule that must hold. */
		conditions: readonly Condition[]
	}
	| {
		op: 'answered'
		/** The question that must be answered. */
		question: string
	}
```

<!-- sample: type-docs-after run -->
```ts
import type { TypeDocs } from '@deviltea/widget-core'
import { createWidgetPlugin, defineTypeDocs } from '@deviltea/widget-core'

type Condition
	= | { op: 'all', conditions: readonly Condition[] }
		| { op: 'answered', question: string }

// Recursive: the annotation is required (TS7022 without it).
const conditionDocs: TypeDocs<Condition> = defineTypeDocs<Condition>('Condition', {
	description: 'A rule over the answers.',
	fields: {
		op: { description: 'The kind of rule.' },
		conditions: { description: 'Every rule that must hold.', items: { ref: () => conditionDocs } },
		question: { description: 'The question that must be answered.' },
	},
})

interface StepRules {
	visibleWhen?: Condition
	completeWhen: Condition
}

// Not recursive: no annotation needed.
const stepRulesDocs = defineTypeDocs<StepRules>('StepRules', {
	description: 'When a step is shown and when it is complete.',
	fields: {
		visibleWhen: { description: 'Shown only while this rule holds; always shown when omitted.', ref: conditionDocs },
		completeWhen: { description: 'Complete once this rule holds.', ref: conditionDocs },
	},
})

const step = createWidgetPlugin('step')
	.description('One step of a form.')
	.interfaces<{ config: { raw: StepRules, resolved: StepRules } }>()
	.config({
		description: 'The step\'s rules.',
		raw: { ref: stepRulesDocs },
		resolved: { ref: stepRulesDocs },
		validate: (input): input is StepRules => typeof input === 'object' && input !== null,
		resolve: raw => raw ?? { completeWhen: { op: 'all', conditions: [] } },
	})
	.done()

console.log(step.docs.config?.raw) // { ref: 'StepRules' }
console.log(Object.keys(step.docs.types)) // [ 'StepRules', 'Condition' ]
console.log(step.docs.types.StepRules?.fields?.visibleWhen?.ref) // Condition
```

### Known limits

- **Depth.** Whether `items` or `values` is required is decided at most four nested arrays or dictionaries deep. A
  closed object type inside five nested arrays is not required to be documented.
- **An index signature with fixed keys** (`{ en: string, [language: string]: string }`) is a dictionary: it takes
  `values`, which documents every value, the fixed keys included. It takes no `fields`.
- **A named type that is one member of a union** (`split: EqualSplit | PercentSplit`) cannot be referred to alone:
  a `ref` names docs of the field's whole type. Document the union's keys in the field's `fields`, and say what
  each member means in the field's description. The documentation generator then has no type-level description of
  its own for `EqualSplit` or `PercentSplit`.
- **A literal alias** (`type RoundStep = 0.01 | 0.05 | 1`) has no inner fields, so there is nothing to `ref`: type
  docs describe object types. Write what the values mean in the description of each field that uses the alias.

## Plugin factories

A factory that builds a family of plugins from one generic interfaces type used to share one JSDoc comment among
every plugin it built. In `0.4` the factory takes the prose as a parameter. Type the docs in the factory's spec over
the spec's own type parameters (`FieldDocs<Raw>`), and the compiler requires each call site to document that
plugin's own fields.

The factory still needs the cast it needed before for a generic interfaces type (see
[Generic plugin factories](../packages/widget-core#generic-plugin-factories)). The docs add no cast:
`FieldDocs<Raw>` is accepted where the config phase wants the docs of `Raw | null`.

TypeScript infers `Raw` and `Resolved` from the spec's callbacks, not from the docs. Annotate the parameters of the
callbacks at the call site, as the sample does with `isRaw` and `resolve`: a callback without annotations leaves the
type parameters at their constraint (`object`), and the docs of the real fields are then rejected.

<!-- sample: factory-docs run -->
```ts
import type { FieldDocs, WidgetPluginConfigPhase } from '@deviltea/widget-core'
import { createWidgetPlugin, defineFieldDocs } from '@deviltea/widget-core'

interface ControlInterfaces<Raw extends object, Resolved extends object> {
	config: { raw: Raw | null, resolved: Resolved }
	state: { answer: string | null }
}

interface ControlSpec<Type extends string, Raw extends object, Resolved extends object> {
	readonly type: Type
	readonly description: string
	readonly config: {
		readonly description: string
		readonly raw: FieldDocs<Raw>
		readonly resolved: FieldDocs<Resolved>
	}
	readonly isRaw: (input: unknown) => input is Raw | null
	readonly resolve: (raw: Raw | null) => Resolved
}

function createControlPlugin<const Type extends string, Raw extends object, Resolved extends object>(
	spec: ControlSpec<Type, Raw, Resolved>,
) {
	type Interfaces = ControlInterfaces<Raw, Resolved>
	return (createWidgetPlugin(spec.type)
		.description(spec.description)
		.interfaces<Interfaces>() as WidgetPluginConfigPhase<Type, Interfaces>)
		.config({ ...spec.config, validate: spec.isRaw, resolve: spec.resolve })
		.state(state => state.answer({
			description: 'The answer as the respondent left it; `null` until answered.',
			validate: (input): input is string | null => input === null || typeof input === 'string',
			default: () => null,
		}))
		.done()
}

interface ShortAnswerRaw {
	placeholder?: string
	format?: 'text' | 'email'
}

const shortAnswer = createControlPlugin({
	type: 'short-answer',
	description: 'A one-line text answer.',
	config: {
		description: 'How the field is shown.',
		// The call site documents this control's own fields; a missing or a stale one is a type error.
		raw: defineFieldDocs<ShortAnswerRaw>()({
			fields: {
				placeholder: { description: 'The hint shown in an empty field.' },
				format: { description: 'The input format; text when omitted.' },
			},
		}),
		resolved: { fields: { format: { description: 'The input format.' } } },
	},
	isRaw: (input: unknown): input is ShortAnswerRaw | null => input === null || typeof input === 'object',
	resolve: (raw: ShortAnswerRaw | null) => ({ format: raw?.format ?? 'text' }),
})

console.log(shortAnswer.docs.description) // A one-line text answer.
console.log(Object.keys(shortAnswer.docs.config?.raw?.fields ?? {})) // [ 'placeholder', 'format' ]
```

## `WidgetRef` replaces `@widgetRef`

A config field that holds the id of another widget was a `string` tagged `@widgetRef A | B` in `0.3`. In `0.4` it is
typed `WidgetRef<'A' | 'B'>`, a branded string exported by Core. Any string is accepted without a cast, a value reads
back as a `string`, and tooling reads the plugin types from the type (`WidgetRefTypesOf`). It is type-level only, like
slot expectations: nothing checks at run time that the id names a widget of those types; the plugin's `validate` or
its structure validation still does that. A reference to more types does not assign to one to fewer:
`WidgetRef<'A' | 'B'>` is not assignable to `WidgetRef<'A'>`.

- **Detect:** nothing at compile time; a generated schema no longer marks the field as a reference.
- **Find:** `rg "@widgetRef"`.
- **Do:** type the field `WidgetRef<...>` with the types the tag named, and delete the tag. A `WidgetRef` takes a
  description only, like any string.

<!-- sample: widget-ref-before before -->
```ts
export interface ConditionRaw {
	/**
	 * The question whose answer is tested.
	 * @widgetRef Rating | Choice
	 */
	question: string
}
```

<!-- sample: widget-ref-after after -->
```ts
import type { WidgetRef } from '@deviltea/widget-core'

export interface ConditionRaw {
	question: WidgetRef<'Rating' | 'Choice'>
}

export const raw: ConditionRaw = { question: 'rating-1' }
export const id: string = raw.question
```

## `undocumented`

`undocumented` is a marker exported by Core, accepted wherever a description or a docs object is required. It
type-checks, and `plugin.docs` holds `null` in its place. Written as a description (`description: undocumented`), it
also waives the nested docs of that entry (its `fields`, `items`, `values`, `params`, `returns`, `payload`,
`details`, `raw` and `resolved`), which stay allowed, and checked, when given. The documentation generator's
`--check` reports every marker, with the plugin and the docs path.

Use it in tests and fixtures instead of placeholder prose, and as a step in a large migration: write `undocumented`
everywhere first so the code compiles, then replace the markers one by one.

<!-- sample: undocumented run -->
```ts
import { createWidgetPlugin, undocumented } from '@deviltea/widget-core'

interface CartLine {
	sku: string
	quantity: number
}

const cart = createWidgetPlugin('cart')
	.description(undocumented)
	.interfaces<{ state: { lines: readonly CartLine[] } }>()
	// `undocumented` as the description: `items` may be left out.
	.state(state => state.lines({
		description: undocumented,
		validate: (input): input is readonly CartLine[] => Array.isArray(input),
		default: () => [],
	}))
	.done()

console.log(cart.docs.description) // null
console.log(cart.docs.state?.lines) // { description: null }
```

## `plugin.docs` {#plugin-docs}

A completed plugin carries its docs as `plugin.docs` (`WidgetPluginDocs`): plain, frozen, serializable data made of
strings, `null`, plain objects and arrays, so `structuredClone` and `JSON.stringify` round-trip it.

| Field | Holds |
| --- | --- |
| `description` | the plugin's description |
| `config` | `{ description, raw?, resolved? }` |
| `slots` | per slot, `{ description }` |
| `state`, `properties` | per member, `{ description, fields?, items?, values?, ref? }` |
| `methods` | per Method, `{ description, params?, returns? }` |
| `events` | per Event, `{ description, payload? }` |
| `reasons` | per reason, `{ description, details? }` |
| `types` | the type docs the plugin refers to with `ref`, by name (transitively) |

A section is `null` when the plugin does not declare it (`reasons`: when `.reasons()` was not called). A description
is `null` where the author wrote `undocumented`, and a nested docs position written as `undocumented` is `null`. A
`ref` is the name of an entry of `types`. Records keep the key order of the objects they were declared with (see
[Event order](#event-order-follows-javascript-key-order)).

The docs are not part of `system.catalog`, `inspectPlugin`, Blueprints or the Inspector protocol; those carry
semantic facts only, as in `0.3`. A host that showed generated documentation can read `plugin.docs` directly
instead. The prose is in every bundle that includes the plugin.

<!-- sample: plugin-docs run -->
```ts
import { createWidgetPlugin, createWidgetSystem } from '@deviltea/widget-core'

const note = createWidgetPlugin('note')
	.description('A short note.')
	.interfaces<{ config: { raw: { text: string }, resolved: { text: string } } }>()
	.config({
		description: 'What the note says.',
		raw: { fields: { text: { description: 'The text, as Markdown.' } } },
		resolved: { fields: { text: { description: 'The text.' } } },
		validate: (input): input is { text: string } => typeof input === 'object' && input !== null && typeof (input as { text?: unknown }).text === 'string',
		resolve: raw => ({ text: raw?.text ?? '' }),
	})
	.done()

console.log(JSON.stringify(structuredClone(note.docs)) === JSON.stringify(note.docs)) // true
console.log(Object.isFrozen(note.docs)) // true
console.log('docs' in (createWidgetSystem({ plugins: [note] }).catalog.widgets[0] ?? {})) // false
```

## Tooling

### The generator is published as `@deviltea/widget-docs-generator` {#the-generator-is-published}

The documentation generator was the repository's private `@deviltea/widget-skills`, which you could only copy or run
from a clone. From `0.4.0` it is the published package `@deviltea/widget-docs-generator`, released together with the
other packages under one version and declaring Core as a peer dependency. It keeps the generator's behaviour: the same
outputs, the docs object (`WIDGET_DOCS_VERSION` `2`) and both schema profiles. See its
[documentation](../packages/widget-docs-generator).

- **Detect:** a copy of `apps/widget-skills`, a script that runs its `src/cli.ts` through a TypeScript loader, or an
  import of `@deviltea/widget-skills/vite`.
- **Find:** `rg "widget-skills"`.
- **Do:** `pnpm add -D @deviltea/widget-docs-generator@^0.4.0` and use what it publishes:
  - the bin `widget-docs-generator` with the same options (it runs with plain Node and needs no loader);
  - `@deviltea/widget-docs-generator/vite` for the Vite plugin, imported by package name from an ES module config;
  - `@deviltea/widget-docs-generator/virtual-widget-docs` (or `-slim`) for the virtual module's type;
  - `@deviltea/widget-docs-generator/runtime` for the flat/tree converter in an application, which imports no
    TypeScript;
  - `@deviltea/widget-docs-generator` (the build-time API) and `/docs` (the docs object types) for everything else.

### Agent Skills ship with the packages {#agent-skills}

New in `0.4.0`: the skills that describe an API and no System ship with the package they describe, versioned with it,
and their code samples are compiled against it before each release. `@deviltea/widget-core` ships
`skills/widget-plugin-authoring/` and `@deviltea/widget-vue` ships `skills/widget-vue-renderer/`. Install them with
the [`skills` CLI](https://github.com/vercel-labs/skills): `npx skills experimental_sync` links the skills of your
installed packages (experimental in `skills` 1.9.0), and `npx skills add DevilTea/widget@v0.4.0` installs both from
the release tag.

The generator writes only the System skills now: `<system>-source-json-authoring` and
`<system>-renderer-implementation`, still in `<out>/skills/<name>/SKILL.md`. It no longer writes
`widget-plugin-authoring`, and the renderer skill refers to `widget-vue-renderer` for the API instead of repeating it.

- **Detect:** a `skills/widget-plugin-authoring/` folder in the generator's output, or a copy of it in your agent's
  skills folder.
- **Find:** `rg -l "name: widget-plugin-authoring"`.
- **Do:** delete the generated copy (`--out` removes it on the next run, through its `.generated.json` manifest; a copy
  elsewhere is yours to delete) and install the skill from `@deviltea/widget-core` as above. Install
  `widget-vue-renderer` beside the generated renderer skill.

### JSDoc is no longer read

JSDoc on an `Interfaces` type, on a named type or on a field is an ordinary code comment again. The documentation
generator takes every description from `plugin.docs`, so it must import the module that creates the System, and
takes the shape from the types, as before. JSDoc you leave in place still shows when an editor hovers a member, but
nothing checks it and no tool reads it.

The JSDoc tags go with it. A description's first paragraph is its summary and the rest are its remarks, so the text
of `@remarks` becomes a second paragraph. `@param` and `@returns` become a Method's `params` and `returns`.
`@example`, `@see`, `@deprecated` and `@defaultValue` have no field of their own: write what matters into the
description (the generated docs object keeps those keys, empty).

- **Detect:** generated documentation with empty descriptions where the JSDoc used to be.
- **Find:** `rg "/\*\*" ` in the files that declare your interfaces types.
- **Do:** move the text into the builder (the sections above), then delete the JSDoc or keep it as a comment.

### Constraint tags are retired

The constraint tags (`@minimum`, `@maximum`, `@exclusiveMinimum`, `@exclusiveMaximum`, `@multipleOf`, `@integer`,
`@minLength`, `@maxLength`, `@pattern`, `@format`, `@minItems`, `@maxItems`, `@uniqueItems`, `@minProperties`,
`@maxProperties`, `@propertyNames`, `@default` and `@examples`) are no longer read, and the generated JSON Schema has
the shape only: no `minimum`, `pattern`, `minItems`, `default` or `integer`. A constraint is prose in the
description, which says what `validate` enforces, and `validate` is the authority, as it was in every version.

- **Detect:** the generated schemas lose their constraint keywords; an editor that offered bounds or defaults from
  them no longer does.
- **Find:** `rg "@(minimum|maximum|exclusiveM(in|ax)imum|multipleOf|integer|minLength|maxLength|pattern|format|minItems|maxItems|uniqueItems|minProperties|maxProperties|propertyNames|default|examples)\b"`.
- **Do:** write each constraint into the description of its field, and make sure `validate` enforces it: the schema
  no longer rejects a value that breaks it.

<!-- sample: constraints-before before -->
```ts
export interface RatingRaw {
	/**
	 * How many steps the scale has.
	 * @integer
	 * @minimum 3
	 * @maximum 10
	 */
	scale: number
}
```

<!-- sample: constraints-after run -->
```ts
import { createWidgetPlugin, createWidgetSystem } from '@deviltea/widget-core'

interface RatingRaw {
	scale: number
}

function isRatingRaw(input: unknown): input is RatingRaw {
	if (typeof input !== 'object' || input === null)
		return false
	const { scale } = input as { scale?: unknown }
	return typeof scale === 'number' && Number.isInteger(scale) && scale >= 3 && scale <= 10
}

const rating = createWidgetPlugin('rating')
	.description('A rating on a scale.')
	.interfaces<{ config: { raw: RatingRaw, resolved: RatingRaw } }>()
	.config({
		description: 'The scale.',
		raw: { fields: { scale: { description: 'How many steps the scale has: an integer from 3 to 10.' } } },
		resolved: { fields: { scale: { description: 'How many steps the scale has.' } } },
		validate: isRatingRaw,
		resolve: raw => raw ?? { scale: 5 },
	})
	.done()

const system = createWidgetSystem({ plugins: [rating] })
console.log(system.createBlueprint({ id: 'r', type: 'rating', config: { scale: 12 } }).status) // invalid
console.log(system.createBlueprint({ id: 'r', type: 'rating', config: { scale: 7 } }).status) // valid
```

### The documentation generator's `--check`

The documentation generator (`@deviltea/widget-docs-generator`, the private `@deviltea/widget-skills` in `0.3`) now
reads `plugin.docs`. Its `--check` reports different problems, and every problem is an error:

| `0.3` | `0.4` |
| --- | --- |
| `missing-doc`: a member, field or named type without JSDoc (an error, or a warning for what only renderers read) | `undocumented`: an `undocumented` marker, with its plugin and docs path. `missing-doc` remains for a plugin without `plugin.docs` and for docs an untyped plugin left out |
| `unknown-tag`, `misplaced-tag` | removed with the tags |
| `name-mismatch`: plugin types, capabilities, slots, State, Properties and Events, types against the runtime | the same, plus Methods, fields, parameters and payload positions between the types and `plugin.docs`, and a `ref` whose type docs name is not the type's name |
| | `docs-conflict`: a named type documented differently in two places |
| | `unused-doc`: a description no output can show |
| | `no-docs`: the System was not imported (`--no-runtime`), so no prose was read |

## Run-time checks of the docs

Completeness is checked by the types only. At run time Core checks that each docs value is well formed when it is
declared, and a malformed value throws a `TypeError` that names the plugin and the docs path, like any other
malformed declaration. A `0.3` plugin definition loaded without type-checking fails on the first of these:

- `.interfaces()` called before `.description()`;
- a description that is not a string or `undocumented`, a missing description included (a `0.3` slot, State,
  Property, Method or config definition has none);
- `.events()` or `.reasons()` given anything but a plain object (prototype `Object.prototype` or `null`): a list, a
  `Map` or a class instance;
- a docs object with a key it does not have, such as a `summary` in an Event entry or in a `fields` entry;
- `params` or `payload` that is not an array, or an array with a hole;
- `fields`, `items`, `values` or `ref` at the top of a config definition (the `0.2` shape);
- a `ref` that is neither type docs from `defineTypeDocs()` nor a function that returns them, or a `ref` beside
  `fields`, `items` or `values`; `done()` resolves the thunks and also rejects two different type docs with one name;
- an exception thrown while the docs are read (a getter, a Proxy trap, a `ref` thunk), which is wrapped in the
  `TypeError`, with the original as its `cause`.

<!-- sample: docs-type-errors run -->
```ts
import { createWidgetPlugin } from '@deviltea/widget-core'

// A `0.3` definition seen as plain JavaScript.
const untyped = createWidgetPlugin('panel') as unknown as {
	interfaces: () => unknown
	description: (text: unknown) => { interfaces: () => { events: (definitions: unknown) => unknown } }
}

try {
	untyped.interfaces()
}
catch (error) {
	console.log(error instanceof TypeError, (error as Error).message)
	// true Widget plugin "panel": phase "interfaces" was called before ".description()"; ...
}

try {
	untyped.description('A panel.')
		.interfaces()
		.events(['pressed'])
}
catch (error) {
	console.log((error as Error).message)
	// Widget plugin "panel": section "events" must be declared with a plain object of docs keyed by name, got array. ...
}
```

## Inspector

`@deviltea/widget-inspector` has no change in `0.4`, and the protocol stays `1.0`: the Blueprint snapshot carries no

## Vue adapter

`@deviltea/widget-vue` has no change in `0.4`: no run-time change and no public type change. Its test fixtures move
to the `0.4` builder like every plugin. The keyed surfaces (`useState()`, `useProperties()`, `useMethods()`, `emit`
and the diagnostics surfaces) are still mapped over `keyof` the Interfaces sections, so a JSDoc comment you keep on
an Interfaces member still shows when an editor hovers it; it is a comment, not the plugin's documentation. The
package now also ships the `widget-vue-renderer` Agent Skill (see [Agent Skills ship with the packages](#agent-skills)).

## Widget Lab

The Widget Lab is a private application, not a released package. Its Structure editor offers what a config's
generated JSON Schema allows, and the schemas no longer carry `minimum`, `minItems` or `default`. An optional number
added in the editor starts at `0`, an added list starts empty, and removing items is not bounded by a minimum count.
Core's diagnostics report each value that breaks a constraint at its field.
