# Migrating from 0.2 to 0.3

This page takes a plugin library, an application or a renderer library from the `0.2` line to `0.3`. While the
packages are `0.x`, a breaking change in any package bumps the minor version of all three
(`@deviltea/widget-core`, `@deviltea/widget-inspector`, `@deviltea/widget-vue`).

`0.3` makes a plugin's `Interfaces` type, with its JSDoc, the single source of the plugin's shape and of its
documentation. Core keeps the semantic facts only: it no longer stores or transports prose or passive schema.
Documentation and JSON Schema are generated from the types by tooling outside Core. The decision is recorded in
[Discussion #12](https://github.com/DevilTea/widget/discussions/12), "Interfaces are the single source of a plugin's
shape and documentation (0.3.0)".

Each entry follows the shape of [Migrating from 0.0.x to 0.1](./0.1): **Detect** says how the change shows itself,
**Find** gives a search that locates the affected code, and **Do** says what to change.

This page covers `@deviltea/widget-core`. The sections for `@deviltea/widget-inspector` and `@deviltea/widget-vue`
are added with their own changes.

## Before you start: install and versions

Upgrade all the Widget packages you use in one change, to the `0.3` line:

```bash
pnpm add @deviltea/widget-core@^0.3.0
pnpm add @deviltea/widget-vue@^0.3.0 @deviltea/widget-inspector@^0.3.0 # only the ones you use
```

A dependent at `0.3.0` declares Core as `^0.3.0` (`>=0.3.0 <0.4.0`), so a `0.2.x` Core no longer satisfies its peer
range: upgrade Core together with the dependents.

## Who needs to do what

| You are | Do |
| --- | --- |
| A plugin author | Every entry under [Plugin builder](#plugin-builder), then [Slots are a record](#slots-are-a-record) |
| A host that reads `system.catalog`, `plugin.description`, `plugin.config`, `plugin.descriptions` or `inspectPlugin` | [Catalog and inspection carry semantic facts only](#catalog-and-inspection-carry-semantic-facts-only) |
| A host that shows a config form from `config.schema` | [`config.schema` is removed](#configschema-is-removed) |
| Anyone | Optional: the [new surface](#new-surface) |

Every breaking change in this page is a compile error in TypeScript. In JavaScript, or in a module loaded without
type-checking, the removed `.description()` phase and the callback form of `.events()` throw a `TypeError` when the
plugin is built; a leftover `description` or `schema` field in a definition object is ignored.

## Plugin builder

The phase order is now:

```text
interfaces -> config? -> slots? -> structure? -> state? -> properties? -> methods? -> events? -> done
```

### `.description()` and the `description` fields are removed

The builder no longer starts with `.description()`, and the `description` fields of the config definition, of every
slot definition and of every Event definition are gone. Move each description into a JSDoc comment on the matching
part of the interfaces type.

- **Detect:** `Property 'description' does not exist on type 'WidgetPluginInterfacesPhase<...>'` at the builder call,
  and an excess-property error on `description` in a config or slot definition.
- **Find:** `rg "\.description\(|description:"` in your plugin sources.
- **Do:** delete the call and the fields, and write the text as JSDoc on the interfaces type.

<!-- sample: plugin-description-before before -->
```ts
import { createWidgetPlugin } from '@deviltea/widget-core'

interface PanelInterfaces {
	config: { raw: { title?: string } | null, resolved: { title: string } }
	slots: 'content'
}

export const panel = createWidgetPlugin('panel')
	.description('A titled container')
	.interfaces<PanelInterfaces>()
	.config({
		description: 'How the panel is titled',
		validate: (input): input is { title?: string } | null => input === null || typeof input === 'object',
		resolve: raw => ({ title: raw?.title ?? '' }),
	})
	.slots({ content: { description: 'The widgets the panel lays out' } })
	.done()
```

<!-- sample: plugin-description-after after -->
```ts
import type { WidgetChild } from '@deviltea/widget-core'
import { createWidgetPlugin } from '@deviltea/widget-core'

/** A titled container. */
interface PanelInterfaces {
	/** How the panel is titled. */
	config: {
		raw: {
			/** The title shown above the content. Empty by default. */
			title?: string
		} | null
		resolved: { title: string }
	}
	slots: {
		/** The widgets the panel lays out. */
		content: WidgetChild
	}
}

export const panel = createWidgetPlugin('panel')
	.interfaces<PanelInterfaces>()
	.config({
		validate: (input): input is { title?: string } | null => input === null || typeof input === 'object',
		resolve: raw => ({ title: raw?.title ?? '' }),
	})
	.slots({ content: {} })
	.done()
```

### `config.schema` is removed

A config definition no longer takes `schema`, and `WidgetConfigJsonSchema`, `WIDGET_CONFIG_JSON_SCHEMA_DIALECT` and
`WidgetPluginConfigMetadata` are no longer exported. Core never validated against the schema; it only carried it. A
JSON Schema for authored config is now generated from `config.raw` (and its JSDoc) by tooling.

- **Detect:** an excess-property error on `schema`, and `Module '"@deviltea/widget-core"' has no exported member
  'WIDGET_CONFIG_JSON_SCHEMA_DIALECT'` (or `WidgetConfigJsonSchema`).
- **Find:** `rg "schema:|WIDGET_CONFIG_JSON_SCHEMA_DIALECT|WidgetConfigJsonSchema|WidgetPluginConfigMetadata"`.
- **Do:** delete the field. A host that needs a schema at run time (for example to render a config form) keeps its
  own map from plugin `type` to schema, filled from the generated schema or from the schema library the plugin
  already uses; see [Using a schema library](../packages/widget-core#using-a-schema-library-zod-valibot-arktype).

<!-- sample: config-schema-before before -->
```ts
import { createWidgetPlugin, WIDGET_CONFIG_JSON_SCHEMA_DIALECT } from '@deviltea/widget-core'

export const badge = createWidgetPlugin('badge')
	.description('A badge')
	.interfaces<{ config: { raw: { label?: string } | null, resolved: { label: string } } }>()
	.config({
		description: 'Badge configuration',
		schema: { $schema: WIDGET_CONFIG_JSON_SCHEMA_DIALECT, type: 'object', properties: { label: { type: 'string' } } },
		validate: (input): input is { label?: string } | null => input === null || typeof input === 'object',
		resolve: raw => ({ label: raw?.label ?? 'Badge' }),
	})
	.done()
```

<!-- sample: config-schema-after after -->
```ts
import { createWidgetPlugin } from '@deviltea/widget-core'

interface BadgeInterfaces {
	/** How the badge is labelled. */
	config: {
		raw: {
			/** The text shown on the badge. Defaults to "Badge". */
			label?: string
		} | null
		resolved: { label: string }
	}
}

export const badge = createWidgetPlugin('badge')
	.interfaces<BadgeInterfaces>()
	.config({
		validate: (input): input is { label?: string } | null => input === null || typeof input === 'object',
		resolve: raw => ({ label: raw?.label ?? 'Badge' }),
	})
	.done()
```

### `.events()` takes the list of Event names

An Event definition held nothing but its description, so the keyed-chain section is gone. `.events(names)` takes the
list of every key of `Interfaces['events']`, each exactly once, in any order. `WidgetEventDefinition` and
`WidgetEventsSection` are no longer exported.

- **Detect:** `Argument of type '(events: any) => any' is not assignable to parameter of type 'readonly (...)[]'` at
  each `.events(` call.
- **Find:** `rg "\.events\("`.
- **Do:** pass the names. A missing name and a name the interfaces do not declare are type errors. Pass a list
  literal or an `as const` array: a widened array such as `('pressed' | 'changed')[]` is rejected, because it may
  hold only some of the names. For an explicitly empty capability write `.events([])`. At run time a value that is
  not a dense array of strings, and a repeated name, throw a `TypeError` that names the plugin and the section.

<!-- sample: events-list-before before -->
```ts
import { createWidgetPlugin } from '@deviltea/widget-core'

export const button = createWidgetPlugin('button')
	.description('A button')
	.interfaces<{ events: { pressed: [], changed: [value: string] } }>()
	.events(events => events
		.pressed({ description: 'The button was pressed' })
		.changed({ description: 'The label changed' }))
	.done()
```

<!-- sample: events-list-after after -->
```ts
import { createWidgetPlugin } from '@deviltea/widget-core'

interface ButtonInterfaces {
	events: {
		/** The button was pressed. */
		pressed: []
		/** The label changed. */
		changed: [value: string]
	}
}

export const button = createWidgetPlugin('button')
	.interfaces<ButtonInterfaces>()
	.events(['pressed', 'changed'])
	.done()
```

## Slots are a record

`Interfaces['slots']` changes from a union of slot names to a record. Each key is a slot name, and each value is
what the plugin expects of the slot's children:

| Expectation | Meaning |
| --- | --- |
| `'notice' \| 'link'` | a union of plugin `type` literals |
| `WidgetContract<{ state?, properties?, methods?, events? }>` | any widget that has these members |
| `WidgetChild` | any widget |

The expectation is **type-level only**. Core adds no runtime check: slot validation stays free-form in
`validateStructure`, and a plugin that declares an expectation is responsible for enforcing it. Runtime behaviour,
slot diagnostics and the authored `slots` field of a widget node do not change.

- **Detect:** `Type '{ slots: "content"; }' does not satisfy the constraint 'WidgetInterfaces'` at `.interfaces<...>()`,
  or an `extends WidgetInterfaces` interface that no longer compiles.
- **Find:** `rg "slots: '|slots: never"` in your interfaces (`slots: never` stays valid and needs no change).
- **Do:** turn each name into a key. Use `WidgetChild` to keep the `0.2` meaning ("any widget"), and narrow later.
  Types that took the slot-name union (`WidgetSlotNameOf`, the `slot` of a structure diagnostic, the keys of a
  node's `slots`) now read the record's keys and need no change.

<!-- sample: slots-record-before before -->
```ts
import { createWidgetPlugin } from '@deviltea/widget-core'

export const page = createWidgetPlugin('page')
	.description('A page')
	.interfaces<{ slots: 'header' | 'body' }>()
	.slots({
		header: { description: 'At most one widget' },
		body: { description: 'The page content' },
	})
	.done()
```

<!-- sample: slots-record-after after -->
```ts
import type { WidgetChild } from '@deviltea/widget-core'
import { createWidgetPlugin } from '@deviltea/widget-core'

interface PageInterfaces {
	slots: {
		/** At most one widget. */
		header: WidgetChild
		/** The page content: notices and links only. */
		body: 'notice' | 'link'
	}
}

export const page = createWidgetPlugin('page')
	.interfaces<PageInterfaces>()
	.slots({
		header: {
			validateStructure: ({ children, addDiagnostic }) => {
				if (children.length > 1)
					addDiagnostic({ message: 'The header accepts at most one widget.', index: 1 })
			},
		},
		body: {},
	})
	.done()
```

Three things follow from an expectation, all of them at the type level:

- `createWidgetSystem` rejects a System in which a slot expects a plugin type that is not registered (the error is
  on `plugins` and names the missing type). Register the plugin, or widen the expectation. A loosely typed System
  (a plugin typed with a broad `string`) is not checked.
- A source typed with the new `WidgetSourceOf<typeof system>` accepts, in each slot, only the sources the slot
  expects. `WidgetSource` and `blueprint.source` are unchanged and accept any registered type in a slot.
- `slot(name)` in `registerDeps` is typed by a `WidgetContract` expectation (see
  [Depending on slot children](#depending-on-slot-children-slotname)).

A broad `string`, a pattern such as `` `x-${string}` ``, a mix of plugin types and a contract, a union of contracts
and `WidgetContract<any>` are rejected at `.interfaces()`.

## Catalog and inspection carry semantic facts only

| Removed | Use instead |
| --- | --- |
| `plugin.description`, `plugin.config`, `plugin.descriptions` | the generated documentation; `plugin.capabilities.config` for presence |
| catalog entry `description`, `config`, `descriptions` | catalog entry `capabilities` and `slots` (the slot names in declaration order, `null` without the capability) |
| `inspectPlugin(plugin).description`, `.config`, and `description` of its slots and Events | the remaining facts: `type`, `capabilities`, `slots`, `state`, `properties`, `events` |
| `description` of a Blueprint inspection Event member, `config` of a resolved Blueprint inspection node | `name`; `capabilities.config` |

- **Detect:** `Property 'description' does not exist on type 'WidgetCatalogEntry'` (or `'descriptions'`, `'config'`),
  and the same on `WidgetPlugin`, `PluginInspection`, `PluginInspectionSlot`, `PluginInspectionEventMember` and
  `BlueprintInspectionEventMember`.
- **Find:** `rg "\.catalog|\.descriptions|inspectPlugin|\.description\b"`.
- **Do:** read prose and schema from the generated documentation, keyed by plugin `type` and member name; the names
  to key by are still in the catalog and in `inspectPlugin`.

<!-- sample: catalog-before before -->
```ts
import type { WidgetSystem } from '@deviltea/widget-core'

export function listWidgets(system: WidgetSystem) {
	return system.catalog.widgets.map(widget => ({
		type: widget.type,
		title: widget.description,
		slots: [...widget.descriptions.slots ?? []].map(([name, description]) => ({ name, description })),
		hasConfig: widget.config !== null,
	}))
}
```

<!-- sample: catalog-after after -->
```ts
import type { WidgetSystem } from '@deviltea/widget-core'

/** The prose your documentation generator emitted, keyed by plugin type. */
type Documentation = Readonly<Record<string, { readonly title: string, readonly slots: Readonly<Record<string, string>> }>>

export function listWidgets(system: WidgetSystem, documentation: Documentation) {
	return system.catalog.widgets.map(widget => ({
		type: widget.type,
		title: documentation[widget.type]?.title ?? widget.type,
		slots: (widget.slots ?? []).map(name => ({ name, description: documentation[widget.type]?.slots[name] ?? '' })),
		hasConfig: widget.capabilities.config,
	}))
}
```

## New surface

Nothing in this section is required for the upgrade.

### Diagnostic reasons and `details`

`Interfaces['reasons']` declares the reasons a plugin reports and the payload of each one. Every plugin-authored
diagnostic input gains `details`, typed by its `reason`, and the resulting Blueprint and Runtime diagnostics carry
it (`details?: JsonValue`).

- A plugin without a `reasons` declaration keeps compiling: `reason` stays any `string`, and `details` is any JSON
  value.
- Once `reasons` is declared, a `reason` that is not one of its keys is a type error, and so is a missing payload,
  a payload on a `void` reason, and `details` without a `reason`.
- `details` must be a JSON value. `addDiagnostic` throws a `TypeError` for anything else; this is a contract
  violation, not a diagnostic.
- `RelativeValueDiagnosticInput`, `RelativeSlotStructureDiagnosticInput` and
  `RelativePluginStructureDiagnosticInput` are now generic over the interfaces (the default keeps the `0.2` shape
  plus `details`), and `WidgetConfigValidateContext` takes the interfaces as an optional type argument. The first
  two changed from an `interface` to a type alias: code that `extends` one of them must intersect instead.

<!-- sample: reasons-before before -->
```ts
import { createWidgetPlugin } from '@deviltea/widget-core'

export const gauge = createWidgetPlugin('gauge')
	.description('A gauge')
	.interfaces<{ state: { level: number } }>()
	.state(state => state.level({
		validate: (input, ctx): input is number => {
			if (typeof input === 'number' && input <= 100)
				return true
			ctx.addDiagnostic({ message: `The level must be at most 100, got ${String(input)}.`, reason: 'too-large' })
			return false
		},
		default: () => 0,
	}))
	.done()
```

<!-- sample: reasons-after after -->
```ts
import { createWidgetPlugin } from '@deviltea/widget-core'

interface GaugeInterfaces {
	state: { level: number }
	reasons: {
		/** The value is not a number. */
		'not-a-number': void
		/** The value is above the gauge's maximum. */
		'too-large': { max: number, received: number }
	}
}

export const gauge = createWidgetPlugin('gauge')
	.interfaces<GaugeInterfaces>()
	.state(state => state.level({
		validate: (input, ctx): input is number => {
			if (typeof input !== 'number') {
				ctx.addDiagnostic({ message: 'The level must be a number.', reason: 'not-a-number' })
				return false
			}
			if (input > 100) {
				ctx.addDiagnostic({ message: 'The level is too large.', reason: 'too-large', details: { max: 100, received: input } })
				return false
			}
			return true
		},
		default: () => 0,
	}))
	.done()
```

### Depending on slot children: `slot(name)`

The `registerDeps` context of a plugin with slots gains `slot(name)`: the resolved children of the widget's own
slot, in Blueprint order, each as a dependency target. It replaces the pattern of reading the children's ids from
the Blueprint and calling `dep.widget(id)` for each; it is sugar over exactly that, not a new target kind.

- A `WidgetContract` expectation types the reads. A `WidgetChild` slot and a slot that expects a union of plugin
  types give untyped reads (refine with `.validate()`), as `dep.widget(id)` does.
- The reads are not checked against the expectation at run time, and `.validate()` stays available.
- A child that did not resolve is left out.

<!-- sample: slot-deps-before before -->
```ts
import { createWidgetPlugin } from '@deviltea/widget-core'

export const wizard = createWidgetPlugin('wizard')
	.description('A wizard')
	.interfaces<{ slots: 'steps', properties: { titles: readonly string[] } }>()
	.slots({ steps: { description: 'The steps, in order' } })
	.properties(properties => properties.titles({
		registerDeps: ({ dep, widget, blueprint }) => blueprint.getChildrenAt(widget, 'steps')
			.flatMap(child => child.id === null
				? []
				: [dep.widget(child.id)
						.properties
						.get('title')
						.validate((value): value is string => typeof value === 'string')]),
		compute: ({ deps }) => deps.map((read) => {
			const title = read()
			return title.ok ? title.value : ''
		}),
	}))
	.done()
```

<!-- sample: slot-deps-after after -->
```ts
import type { WidgetContract } from '@deviltea/widget-core'
import { createWidgetPlugin } from '@deviltea/widget-core'

interface WizardInterfaces {
	slots: {
		/** The steps, in order. */
		steps: WidgetContract<{ properties: { title: string } }>
	}
	properties: { titles: readonly string[] }
}

export const wizard = createWidgetPlugin('wizard')
	.interfaces<WizardInterfaces>()
	.slots({ steps: {} })
	.properties(properties => properties.titles({
		registerDeps: ({ slot }) => slot('steps')
			.map(step => step.properties.get('title')),
		compute: ({ deps }) => deps.map((read) => {
			const title = read()
			return title.ok ? title.value : ''
		}),
	}))
	.done()
```

### `WidgetSourceOf`

`WidgetSourceOf<typeof system>` types a source written in TypeScript: the node grammar (`id`, `type`, `config`,
`slots`, `meta`), with `config` typed per plugin `type` and the children of each slot narrowed to what the slot
expects. `createBlueprint` still takes `unknown`, and a compiled Blueprint's `source` keeps the unnarrowed
`WidgetSource` type.

<!-- sample: source-of-after after -->
```ts
import type { WidgetSourceOf } from '@deviltea/widget-core'
import { createWidgetPlugin, createWidgetSystem } from '@deviltea/widget-core'

const notice = createWidgetPlugin('notice')
	.interfaces<{ config: { raw: { text: string }, resolved: { text: string } } }>()
	.config({
		validate: (input): input is { text: string } => typeof input === 'object' && input !== null && typeof (input as { text?: unknown }).text === 'string',
		resolve: raw => ({ text: raw?.text ?? '' }),
	})
	.done()
const page = createWidgetPlugin('page')
	.interfaces<{ slots: { body: 'notice' } }>()
	.slots({ body: {} })
	.done()

const system = createWidgetSystem({ plugins: [page, notice] })

export const source: WidgetSourceOf<typeof system> = {
	id: 'page-1',
	type: 'page',
	slots: { body: [{ id: 'notice-1', type: 'notice', config: { text: 'Hello' } }] },
}
export const blueprint = system.createBlueprint(source)
```
