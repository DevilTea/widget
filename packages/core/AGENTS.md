# AGENTS.md — @deviltea/widget-core

## Scope and layout

Renderer-agnostic widget composition core: `WidgetPlugin` builder, `WidgetSystem`, `WidgetSystemBlueprint` (compilation/recovery/diagnostics), and `WidgetSystemRuntime` (alien-signals-backed execution). The current normative semantic contract lives in `DevilTea/widget` Discussion #12 under the "Core composition architecture" topic, including its migrated historical decisions and any later accepted amendments. Current `DevilTea/widget` decisions supersede the historical source repository.

- `src/index.ts` — public entry; only export the public contract surface.
- `src/inspection/` — the dedicated, strictly readonly `@deviltea/widget-core/inspection` subpath
  (`inspectPlugin`, `inspectBlueprint`, `inspectRuntime`). Not re-exported from `src/index.ts`. It is a supported
  surface for any host, not only DevTools. `inspectPlugin(plugin)` is a superset of the `system.catalog` entry (`type`,
  `capabilities`, slot names, plus the State/Property/Event member facts), so a host holding only a
  plugin can list its members. Catalog and inspection carry semantic facts only: no descriptions, no config metadata and
  no schema; the prose lives on `plugin.docs` only (Discussion #12, "Descriptions live in the plugin builder; JSON Schema is inferred from the types (0.4.0)"). Normative contract: `DevilTea/widget` Discussion #12, Core composition architecture topic,
  including the migrated historical decisions (the "inspection exact API v1" parts 1 and 2 and the earlier
  readonly-subpath/identity/disposal inspection amendments, originally `DevilTea/deviltea-labs#10`).
- `src/integration/` — the `@deviltea/widget-core/integration` subpath, a narrow renderer-integration
  bridge that is not re-exported from `src/index.ts` (renderer adapters use it to obtain only the
  current widget's event emitter).
- `src/**/*.unit.test.ts` — colocated Vitest unit tests (run by the root config too).
- `skills/widget-plugin-authoring/` — the Agent Skill this package ships (`SKILL.md` plus `references/plugin-docs.md` and `references/example-interfaces.md`), listed in `files` and published with the package (Discussion #12 amendment "`@deviltea/widget-docs-generator` is a published package", point 3). It is part of the package: an API change that it describes (the builder phases, the docs rules, diagnostics, the System) updates it in the same PR. Its `ts` samples are compiled, and run where marked `run`, by `scripts/docs-samples.unit.test.ts` like the documentation's, so a change that breaks one fails CI. The layout `skills/<name>/SKILL.md`, with a frontmatter `name` equal to the folder's name and a `description`, is what `npx skills` reads. Write the frontmatter as exactly two lines, `name: <lowercase-kebab>` and `description: "<one JSON double-quoted string>"`: the CLI parses it as YAML and silently skips a skill it cannot parse (an unquoted value holding `: `, for one), and the checks accept only this spelling; `scripts/package-skills.unit.test.ts` and CI's packed-consumer job (`scripts/packed-consumer-skills.mjs`) check it, and the root `skills.sh.json` lists `./packages/core/skills` for `npx skills add DevilTea/widget@v<version>`. The skill stands alone: it never tells a reader to import `@deviltea/widget-docs-generator`, and never claims a failing Method is rolled back.
- `tsdown.config.ts` — ESM build with declaration output from `tsconfig.package.json`; three entries
  (`src/index.ts`, `src/inspection/index.ts`, `src/integration/index.ts`) back the root export and the
  `./inspection` and `./integration` subpaths in the `package.json` `exports` map.

## Implementation rules

- Do not resolve implementation difficulty by silently restoring a design that Discussion #12's Core history marks discarded/superseded; a genuine durable semantic change must be recorded in the relevant current `DevilTea/widget` authority before implementation.
- `alien-signals` owns reactive graph/lazy/cache/batch mechanics; this package only implements observable semantics on top of it. Upgrading `alien-signals` requires rerunning the full conformance suite; upstream behavior change is a compatibility conflict, not permission to alter public Runtime semantics.
- Core stays minimal: editor operations, persistence envelopes/versioning/migration, metadata, and renderer/UI concerns stay out of this package.
- All framework-owned semantic callbacks are synchronous; a returned Promise/thenable is an implementation contract violation, not an Issue. For `void`-returning Methods and the structure validators (slot, plugin, system) a callback whose own inferred return type is a thenable is also a type error where it is written into the builder or the System options and the declared return is one a thenable is assignable to (`void`, `unknown`, `{}`, `object`); standalone definition types cannot infer and accept any return, and the runtime guard still throws.
- A plugin's `Interfaces` type is the single source of its shape; its prose is written in the builder, beside each definition (Discussion #12, "Descriptions live in the plugin builder; JSON Schema is inferred from the types (0.4.0)", https://github.com/DevilTea/widget/discussions/12#discussioncomment-19850339, which amends the 0.3 "Interfaces are the single source" decision). JSDoc is an ordinary comment that no tool reads. Core stores the prose as plain, serializable data on `plugin.docs` (`src/docs.ts`; `null` where the author wrote `undocumented`, `ref`s resolved to names in `types`) and never reads it. Do not add prose, a schema or config metadata to the catalog, inspection, Blueprints or the Inspector protocol; JSON Schema is inferred from the types by tooling outside Core.
- Docs rules (`src/docs.ts`). Completeness is type-only: `FieldDocs<T>` requires `fields` with an entry for every key of every member of a closed object type (optional keys included), `items` / `values` when an array's element / a dictionary's value needs docs of its own, and nothing for primitives, literal unions, functions, `unknown`, `any`, branded strings (`WidgetRef`) and built-in objects (`Date`, `RegExp`, `Map`/`Set` and their read-only and weak forms, `Promise`, `Error` with `stack`, `ArrayBuffer`, `DataView`, typed arrays; a class of your own stays an ordinary object type); `null` / `undefined` are ignored. Known limits: an index signature mixed with fixed keys is a dictionary (`values` only), and the `items` / `values` requirement looks at most four nested arrays or dictionaries deep. `ref` (shared `defineTypeDocs` docs, or a thunk for recursion) replaces inline docs, must name docs of exactly the field's object type (invariant brand), and excludes them. Exactness: the builder sections and `defineTypeDocs` get TypeScript's fresh-literal excess check only, so a stale key that arrives through a spread or a variable is caught by `defineFieldDocs<T>()(docs)` alone, which is exact at every depth, a `ref` where the value has no object part included (amendment point 8 names it as the exactness check); do not turn `.config()` or the member signatures into const generics for this. A recursive `defineTypeDocs` needs an explicit `: TypeDocs<T>` annotation (TS7022). Unknown docs keys are reported as `WidgetDocsKeyViolation`. `undocumented` is a string-literal marker (a `unique symbol` would widen in variables) accepted for any description or docs object; as a description it waives the entry's nested docs, which stay checked when given. At run time every docs value is checked when it is declared (a description is a string or `undocumented`; a docs object has only its known keys; `ref` is type docs or a function) and captured by value; an exception thrown while reading the docs (a getter, a Proxy trap, a `ref` thunk) becomes a `TypeError` naming plugin and docs path, with the original as `cause`; `fields`/`items`/`values`/`ref` at the top of `.config()` (the 0.2 shape) throw, since the docs go under `raw`/`resolved`; a thunk is resolved by `done()`, which also rejects two different type docs with one name. Never add a runtime completeness check. `WidgetRef<Types>` is type-level only, like slot expectations.
- Builder phase order is `description → interfaces → config? → slots? → structure? → state? → properties? → methods? → events? → reasons? → done`. `.description(text)` must come first at run time too (`.interfaces()` before it throws a `TypeError`); after `.interfaces()` the runtime builder is order-agnostic. `.events(definitions)` takes one docs entry per Event of `Interfaces['events']`, keyed by name (a missing name is a type error, and an undeclared name is one also when the record arrives through a variable; this covers the names only, the entries get the fresh-literal check); the keys are the Events declared at run time, in JavaScript key order (integer-like names first), and a value that is not a plain object of docs (prototype `Object.prototype` or `null`; also for `.reasons()`), or a malformed entry, throws the same `TypeError` as any malformed declaration. `.reasons(definitions)` exists, and is required, when `Interfaces['reasons']` is declared; it records docs only (`reasons` stays no capability). A Method's `params` is required when it has a parameter (a rest parameter needs at least one entry, after one per fixed parameter) and `returns` when it returns a value (not for `void`, `undefined`, `void | undefined` or `never`); a reason's `details` when its payload is not `void`. `.structure(validateStructure)` is the optional plugin-level structure validator, available to every plugin and not a capability (it never appears in `plugin.capabilities`, the catalog or inspection); `.slots(definitions)` takes one argument. Section builders are sealed, definitions are captured by value, and a malformed declaration throws a `TypeError` naming plugin, section, member and field when the plugin is built. A Method declares the Events it may emit in `emits` (an array of Event names, validated against the `events` section, which is declared after the Methods: a non-array or holey value throws from the member call inside `.methods()`, an unknown name or a duplicate from `done()`; `emits` is required in `WidgetMethodDefinition` whenever its `Emits` is not `never`); its `emit` carries only those, statically (`WidgetMethodEventEmitter`) and at run time (the shared per-plugin stand-ins for the other Events are a frozen prototype). `emit` is built lazily per Method, so a Method without `emits` allocates nothing per widget.
- Callback contexts are bounded to their synchronous call: `addDiagnostic` / `hasAnyDiagnostic` close when the callback returns, and `deps.*` / `emit` callables work only while their own callback is the innermost running callback (an `emit` belongs to one Method, not to its widget); they are also closed while foreign code runs (any listener, and plugin callbacks that own no callables: State `validate`, `validateArgs`, `default`, dependency refinements, compilation callbacks), and the one accepted gap is that a callable retained from an earlier invocation can be used by the same member's own later invocation (otherwise an uncoded `TypeError`; after dispose `WidgetSystemRuntimeDisposedError`; the one exception is an `emit` callable for an Event its Method did not declare, which is always a `TypeError`, before and after disposal, because the stand-in is shared per plugin and has no Runtime to ask). A Property can never write State through its dependencies (no `state.set` dependency, and a Method's setter is closed while a Property computes); a `compute`, refinement or `validateArgs` that writes, invokes, resets or disposes through a Runtime held by closure is not prevented, only documented as unsupported (guide, "When Property inspection listeners run").
- Observer exceptions are isolated, with one exception: public Event listener isolation lets the emit re-entrancy guard error (`WidgetSystemRuntimeReentrancyError`, code `emit-depth-exceeded`, thrown when emits nest deeper than the internal limit within one Runtime) and an engine stack overflow through to the outermost caller; every other listener kind isolates everything. A throwing State, Property, diagnostic, Event, disposal, inspection or `WidgetDocument` listener never reaches the writer (for a disposal listener, the `dispose()` caller) or the other listeners and is reported through `queueMicrotask`, or, when the host set one with `setIsolatedErrorHandler` (which returns the handler it replaces), handed to that realm-wide handler in the one hand-over pass of `src/runtime/adapter.ts` (`deliverQueued`): after the outermost Runtime operation when one is in progress, started at once otherwise. The handler is never re-entered (what its own calls isolate waits until it returns) and never runs during an evaluation, dirty check or flush, except inside the flush of a host-held alien-signals batch (unsupported). A chain of reports caused by the handler's handling is bounded by depth (`MAX_HANDLER_CAUSED_DEPTH`) and in total per pass (`MAX_HANDLER_CAUSED_REPORTS`). What the handler does not take (its own exception, a report queued when it is removed, reports beyond a bound) goes to a guarded `queueMicrotask` that never throws: without the global that one report is dropped. Every isolated report goes through `reportIsolatedException` / `reportTrackedReadException`; do not add a report path around them. This amends the earlier rule that a throwing public Event listener propagated to the emitter. A throwing Property `compute` never makes a writer throw; `get()` and dependency reads still rethrow.
- Source and Blueprint rules: a widget node's recognized own keys are `id`, `type`, `config`, `slots` and `meta` (`meta` is the reserved extension key); any other key is `unexpected-widget-field`. Duplicate ids are `duplicate-widget-id`. `MAX_JSON_DEPTH` (256) bounds authored source and SourcePatch operands; no entry point may throw `RangeError` for deep input. `createBlueprintFromJson(text)` is equivalent to `createBlueprint(JSON.parse(text))`, including its diagnostics.
- A Method is read-only when it neither writes State nor emits an Event, itself or through the Methods it invokes, and a Property may depend only on a read-only Method: one `property-dependency-has-side-effects` diagnostic per unique Property and Method pair, whose message names the effect. The compiler seeds both effects (resolved `state.set` leaves, declared `emits`) into one fixed point over Method-to-Method edges in `blueprint/graph.ts`; do not add a second diagnostic code or a second analysis. Like "a Property can never write State", the rule covers declared dependencies only: a `compute` that invokes a Method (which may write or emit) through a Runtime held by closure, or emits through a renderer emitter from `@deviltea/widget-core/integration`, is not prevented, only documented as unsupported (guide, "When Property inspection listeners run").
- Property and Method success values are typed `T` (never `T | null`); only `RuntimeState.get()` and optional dependency reads keep `null`.
- Reading a Property is not bounded by the engine stack: Core bounds with an internal constant how deeply Property evaluations nest, first evaluations and re-evaluations alike, and a read that would nest deeper abandons the evaluations in progress and completes them, deepest first, before it returns. An abandoned run commits nothing (no cached result, no diagnostics, no inspection completion), leaves its computed dirty with every dependency link, and completing the read leaves nothing to evaluate again or to notify without a State write; the host observes only `compute` running more than once within one read (about twice per Property for a chain evaluated beyond the limit) and a different evaluation order. The internal abandonment never reaches a Method, a listener or the host (plugin code that keeps it and throws it later throws an ordinary compute exception). Method-to-Method recursion stays ordinary recursion, and an engine stack overflow stays the last line of defence: the read throws the engine's `RangeError`, and when the host had less stack left than one bounded read needs, a value can stay stale until a write reaches it. The alien-signals internals relied on are listed in `src/runtime/property.ts` (ALIEN-SIGNALS COUPLING) and pinned by `src/runtime/alien-signals-coupling.unit.test.ts` (Discussion #12, "Property dependency chains are not bounded by the engine stack", https://github.com/DevilTea/widget/discussions/12#discussioncomment-19593596).
- Documentation (`docs/site/packages/widget-core.md`, `README.md`) carries code samples; every sample must type-check and, where it is runnable, run against the built package. `scripts/docs-samples.unit.test.ts` enforces this for samples marked `<!-- sample: <name> before|after|run|skip -->`; see the root `AGENTS.md` testing policy for the marker and how output comments are compared.
- The `src/inspection/` subpath is strictly readonly: it must never activate lazy Properties, execute Methods, mutate State, or otherwise widen the alien-signals reactive graph. It projects facts from compiler/runtime-authoritative data only — never by reconstructing status from Issues, and never by running its own SCC/write-effect/emit-effect analysis (`transitivelyWrites` and `transitivelyEmits` come off the compiler). Inspection does not expose the declared `emits`, and `inspectPlugin` has no Method inventory.
- `Interfaces['slots']` is a record of slot name to expectation: a finite union of plugin `type` literals, exactly one `WidgetContract<Shape, Types = never>` (`Shape` is `{ state?, properties?, methods?, events? }` and types the reads; the optional `Types` names the expected plugin types), or `WidgetChild` (any widget). A union of contracts, `WidgetContract<any>`, a non-literal type name and a slot mixing a plugin type with a contract are rejected at `.interfaces()` (Discussion #12 amendment "typed child reads for plugin-type slots"). The expectation is type-level only: never add a runtime check for it; slot validation stays free-form in `validateStructure`. Every use of "the slot names" (`WidgetSlotNameOf`, slot definitions, structure contexts, typed sources) reads the record's keys. The expectation types three things and nothing else: the reads of `slot(name)` (by `Shape`), `createWidgetSystem`'s checks (every plugin type a slot names, in a plain union or in `Types`, is registered; every plugin a contract names satisfies `Shape`, member by member, with an error naming the plugin and the member, by the variance of the section: `state` invariant (mutually assignable, because a parent may read and write it through dependencies), `properties` covariant (read-only), `methods` compared as argument tuples and results so that method-style signatures get no parameter bivariance (the contract's arguments are accepted, arity included; the result is assignable, and a contract `void` accepts any), `events` existence only (no dependency reaches an Event); a contract without `Types` and a loosely typed System are not checked), and the slot children of `WidgetSourceOf<System>` (narrowed to the named types; `WidgetSlotPluginTypeOf` exposes them to renderers). `WidgetSource` (the type of a valid Blueprint's `source`) must not narrow slot children, because nothing checked them.
- `registerDeps` contexts of a plugin with slots have `slot(name)`: the resolved children of the widget's own slot in Blueprint order, each the target `dep.widget(child.id)` returns. It is sugar, not a new target kind (DevilTea/widget#3 stands): do not add a dependency target type, a reference shape or a resolution path for it. A `WidgetContract` types the reads by its `Shape`, with or without `Types`; a plain union of plugin types gives untyped reads (the unknown grammar), by decision: a plugin is typed before any System exists, so a type name alone cannot type a child. Reads are never checked against the expectation at run time, and `.validate()` stays available.
- `Interfaces['reasons']` (not a capability: its `.reasons()` phase records docs only, and it is not in `plugin.capabilities`, the catalog or inspection) types `reason` and `details` of every plugin-authored diagnostic input (`DiagnosticReasonFields`): `details` is the reason's payload, forbidden for `void`; without a declaration `reason` is a `string` and `details` a `JsonValue`, which is also what the System-level validator always gets. `details` must be a JSON value: `addDiagnostic` throws a `TypeError` otherwise (a contract violation, never a diagnostic), in every collector (`assertDiagnosticDetails`). Diagnostics carry `details` by reference through Blueprint, Runtime and inspection; a new plugin-authored diagnostic path must carry it too.
- Capability presence (`config`/`slots`/`state`/`properties`/`methods`/`events`) is required-key *declaration*, independent of the capability's own payload type (Discussion #12's migrated "declaration-presence semantics and public `WidgetPlugin.capabilities`" amendment). Use `HasWidgetCapability<Interfaces, Key>` for any presence gate; never derive presence from `[WidgetCapabilityOf<Interfaces, Key>] extends [never]` — a legitimately-present capability can itself have payload `never` (`slots: never` is the canonical explicit-empty spelling; an empty record is explicit-empty too). A completed `WidgetPlugin` exposes these facts at runtime as `plugin.capabilities`.

## Unit-test standard

- Follow the conformance test matrix preserved in Discussion #12's Core topic: test public semantics and public type behavior, not internal algorithms (no SCC-algorithm, registry-shape, signal-topology, or message-wording assertions).
- Keep the regression cases the matrix marks as must-preserve (optional-only-suppresses-cardinality-0, method-only SCC validity, NaN/±0 strictness, batch non-rollback, post-dispose error surface, etc.; the post-dispose surface of callables is `WidgetSystemRuntimeDisposedError` except that undeclared `emit` stand-ins stay a `TypeError`).
